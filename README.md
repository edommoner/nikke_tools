# NIKKE TOOLS — ローカル編成ラボ

MacBookへの開発移行とCUDA／Metalの共通化を進めています。[移行手順と未解決事項](docs/mac-migration.md)を参照してください。現時点で通常画面のGPU計算はCUDA専用です。小さな共通ソースのMetal実証4ケースはApple M5で実GPU実行済みです。さらに共通binary64候補の14,034ケースがMetalでbit一致しました。[数値規約と残作業](docs/portable-numerics.md)を参照してください。整数変換とコア命中確率powを含む34,874件、共通イベント実行器16ケースをMetalで検証し、[ローカルAPIへ接続](docs/portable-event-runtime.md)しました。通常画面の自律戦闘と全キャラ対応は未完了です。Macでは `./Start-NikkeTools.command` で起動します。

GitHubには現行のソース、GPU生成物、検証スクリプトと記録を保存しています。`research/ports/`・`research/staging/` の過去版／実験用コピー、CUDAキャッシュ、所持データ等の `local-data/`、認証情報はGit管理の対象外です。過去版との比較スクリプトには、ローカルに保存した過去版が別途必要です。計算エンジンの固定版は `powershell -File scripts/setup-engine.ps1` で取得できます。

所持・育成データに基づくダメージ比較、育成条件の探索、重複なしのレイド部隊候補探索の試作です。計算はPC内のPythonプロセスで実行し、UIは127.0.0.1のみで配信します。外部サービスへの公開・育成データの送信は行いません。

計算エンジンは `research/upstream/nikke-calc-master` に取得済みです。このディレクトリはGit対象外です。別のチェックアウトでは `powershell -File scripts/setup-engine.ps1` で固定版を取得してください。

## 最初の操作

1. 上部の「所持・育成データ」からJSONを読み込みます。「デモで操作を試す」では203人分の仮想データを使えます。
2. 上部でレイドの種類・敵属性・戦闘時間・防御力を設定します。レベルやコア条件は「詳細条件」から変更できます。
3. 左側の部隊の枠を選び、右側の画像付きキャラ一覧から追加します。名前検索・バースト・武器・属性で絞り込めます。配置順がバーストの優先順です。編成済みキャラの移動は入れ替えになります。
4. カードの歯車からスキル・オバロ・キューブ・仮ステータスを変更し、「変更を反映して閉じる」を押します。取り込み時のスキル値も同じ画面に表示します。
5. 上部の「詳細計算」でCPU／GPU詳細／GPU詳細＋CPU照合を選びます。GPUが利用可能ならCPU照合付きが初期値です。各部隊の「この部隊を計算」で取り込み時と変更後を比較します。「編成済みの部隊をまとめて計算」では5枠が埋まった部隊を計算し、各部隊と合計のダメージを表示します。
6. 「おすすめ5部隊を探す」から探索を開始し、「この5部隊を編成に入れる」でまとめて採用できます。除外キャラは右側の一覧で選択します。探索後に80 / 160候補へ続行できます。
7. 「計算結果」タブで比較結果を確認し、比較基準の保存や「目標探索」へ進みます。育成や戦闘条件を変更した部隊には再計算が必要な表示が出ます。

原本の取り込みスナップショットと検討案は分離しています。「不足情報として補完」は作業用の基準データに適用し、取り込みスナップショットは保持します。入力欄を編集しただけでは反映されないため、反映ボタンを押してください。

自動バースト・チャージ武器・所持装備を組み合わせた照合は `python scripts/verify-owned-detail.py` で実行します。実スキルを保持した5人編成について、取り込み時／育成変更・仮ステータス／逆順配置、射撃オート／キャラ別運用、固定ゲージ／実蓄積、マストの自動／周期ルール／3の倍数優先を比較します。nativeとPTXを選べ、結果は `research/detail-owned-acceptance.json` に保存します。部隊合計・5人のダメージ・基礎ステータス・バースト履歴・運用設定・最終乱数状態を照合します。検証データは架空の育成値で、実アカウントからの取得成功や全キャラ対応を示すものではありません。

v26の通常画面での再確認は `research/detail-owned-current-ui-verification.json`、通常APIでの育成比較・まとめて計算・設定別キャッシュ・未対応時のCPU切替は `research/detail-owned-current-api-verification.json` に記録しています。CPU照合ではダメージ等に加えて、射撃運用・ゲージ方式・バースト周期設定も一致を必須にしています。v27の記録は下記の味方HP条件の項を参照してください。旧版の記録は `research/detail-owned-ui-verification.json` と `research/detail-owned-api-verification.json` に保持しています。

この組み合わせ検証はnative／PTX各18、計36ケースです。照合だけでなく、育成変更と配置変更で実際にダメージが変わることも合格条件にしています。v26の結果は `research/ports/v26/detail-owned-acceptance.json` と `research/detail-owned-current-summary.json` に保存しています。`scripts/summarize-owned-acceptance.py` は通常APIログ・通常画面・36ケースのソースハッシュを確認して要約を作成するもので、古い版の記録は現行版として受け付けません。v24の要約は `research/detail-owned-summary.json` です。

## 絞り込み・ソート・1部隊計算

右側の「属性」で風圧・水冷・灼熱・電撃・鉄甲を絞り込めます。武器・バースト・名前検索と併用できます。「並び順」は戦闘力の記録値、凸数＋コア強化、スキルLv合計、バーストLv、好感度、取り込み時Lv、宝もの段階、名前に対応します。昇順・降順を選べ、未取得の値はどちらでも末尾です。育成値の並び替えには現在の検討案を使います。

戦闘力はダメージの指標ではなく、取り込み・手入力時点の記録です。原始JSONに数値の `characters[].combat_power` がある場合は `_observed_combat_power` に保持します。このAPI項目が実アカウントから取得できるかは未検証で、ない場合は歯車の「ゲーム内の戦闘力」から入力できます。育成プロファイルの `_observed_combat_power` も読み込めます。育成変更後の戦闘力の再計算はしません。取り込み時Lvは `_observed_level` です。デモには実際の戦闘力はありません。

上部の「1部隊計算」は5部隊から1部隊を選んで編集・計算し、同じ画面の下に取り込み時との比較結果を表示します。編成は5部隊画面と共有します。1部隊用のおすすめを採用した場合、他部隊と重なるキャラは移動し、移動元は空き枠になります。

## 敵プリセット

上部の「敵プリセット」で切り替えます。「詳細条件」から現在の防御力・属性・戦闘レベル・時間・コア径・距離を名前付きで30件まで保存できます。同じ画面内の同じ保存名は更新します。ソロ・ユニオン・1部隊計算の敵条件と自作プリセットは別々に保持します。旧版の画面区分のない自作プリセットは1部隊計算で表示します。保存先はブラウザのlocalStorageで、JSON書き出しにも含みます。自作プリセットは削除できます。

組み込みはEnikkの公開GraphQL APIから取得したソロS1〜S42の42条件と、ユニオンR26〜R45の難易度別300条件です。ソロはソロの情報、ユニオンはユニオンの情報だけを表示します。1部隊計算では両方のデータを参照できますが、選択や編集値は他の画面と独立しています。

属性・防御力・戦闘時間・ニケLv・コア径・距離の6項目が一致する組み込み条件は1項目にまとめます。現データではソロ5組・ユニオン10組です。「詳細条件」の「まとめた開催・ボス一覧」から元の条件を確認できます。HPやギミックなど計算未対応の項目まで同一という意味ではありません。

防御力は各シーズンの `stats.level_defence × monster_obj.defence_ratio / 10000`、敵属性は `monster_obj.element_id.element`、戦闘時間は `wave_obj.battle_time` から取り込みます。収録値と出典・取得日時は `data/raid-presets.json` に保存しています。再取得はソロが `scripts/fetch-raid-presets.py`、ユニオンが `scripts/fetch-union-presets.py` です。両方を更新しても、もう片方の取得データは保持します。現在のAPIが提供する過去シーズンのデータで、各開催時点の完全な保存版と同一であることは保証しません。

ソロAPIの敵ステータスは敵Lv390です。ユニオンの敵Lvは開催・難易度ごとに異なります。画面の戦闘レベル400はニケ側の比較条件で、別の値です。コアなし・距離30mは仮定として適用時に表示します。ボス固有の移動・パーツ破壊・ギミックは含みません。開催期間はこのAPIにないため推測で補っていません。[出典：Enikk Solo Raid Archive](https://enikk.app/soloraid)。

## バースト周期と配置

従来の全員オートでは、エンジンのキャラ別運用ルールも無効でした。今回「詳細条件」の「バースト運用」に次を追加しました。新しく開く画面の初期値は「周期ルールを適用」です。旧版の保存JSONに運用設定がない場合は全員オートとして復元し、以前の前提を保ちます。

- 全員オート：左からの優先順位とクールタイムに従います。
- 周期ルールを適用：所持育成・配置でエンジンの条件付きルールを解決し、**バースト制御だけ**を適用します。手動速射などの射撃ルールは有効にしません。
- マスト3の倍数優先：マスト：ロマンチックメイドに3の倍数の優先指定を明示します。他キャラの周期ルールは適用しません。

固定版のマストのルールは、同段階の20秒以下の仲間がいる場合、左端なら1/3/5/9/11/14回目、左端以外なら3の倍数です。相方が40秒の場合など条件が合わなければ、このルールは適用されません。**周期指定は発動禁止ではなく優先順位**です。他の候補全員がクールタイム中なら、指定外でも発動します。「最大効果」の保証ではありません。マスト不在の部隊では3の倍数指定は適用されず、全員オートで計算し、結果に警告を表示します。画面でも不在の場合はマスト専用の選択肢を無効にします。計算結果の「バースト運用・実際の発動履歴」で適用周期と各回の発動キャラ・時刻を確認できます。

配置は画面の左から順にエンジンへ渡します。左優先のバースト、隣接対象・右側対象の効果など、エンジンに実装済みの処理はその順序を読みます。配置によるマストのルール選択と、隣接・右側の対象選択をテストしています。全キャラの全効果を実測検証したものではなく、5人の120通りの配置やバースト操作自体の最適化探索は未実装です。

## CPU・GPUの計算

探索画面の「計算方法」で「GPUで戦闘概算 → CPUで詳細」を選択できます。CUDA対応NVIDIA GPUの実行テストに成功すると選べます。推薦探索は次の順序です。

1. 所持・育成データから最大800編成を生成（CPUのみの場合は従来の160編成）。
2. CPUで育成を検証し、基礎ステータスと対応効果を固定長配列へ変換。この段階ではCPUの戦闘シミュレーションを実行しません。
3. `app/combat.cu` のCUDAカーネルが1編成を1スレッドに割り当て、最大180秒を60fpsで進めます。射撃間隔、MGの加速、チャージ、弾数、リロード、通常バーストの段階・クールダウン、対応効果の発動・期限・スタック、通常攻撃とスキルのダメージをGPUで計算します。
4. 概算合計が高い5部隊の候補組を優先し、残りを概算順に並べます。選んだ20 / 80 / 160編成を既存のCPUエンジンで詳細計算します。追加探索は並び順と計算済み結果を引き継ぎます。
5. 詳細結果から重複なしの部隊を選択。GPUが使える場合は重複判定・整数合計・順位付けもCUDAで処理します。

**GPU戦闘は新しい概算モデルです。既存エンジンと同じ精度の完全GPU移植ではありません。** 推薦のダメージ・キャラ別内訳・目標達成判定には、戦闘条件バーで選んだ詳細計算方式の値を使います。GPUで低く評価され、詳細計算に残らなかった強い編成があり得ます。CPUだけの探索より良い推薦になることや、全候補の最適解は保証しません。単独部隊の比較・育成逆算・まとめて計算でも、下記の詳細GPU方式を選べます。

概算は攻撃力・防御減・クリティカル・チャージ・ダメージ増・属性・弾数・リロードなど24種類の効果を扱います。開始時、一定秒数、射撃・命中回数、最終弾、リロード終了、フルチャージ、バーストの発動タイミングに対応します。受け取った効果の条件・対象・追加指定が未対応なら、その効果全体を概算から外し、画面の「GPU概算の未対応・近似」にキャラ・効果・理由を表示します。

武器変更、固有状態の連鎖、回復による効果発動、HP・DEF由来の変換、弾数期限、配置条件、特殊バースト段階などは未対応です。一般モデルにも近似があります。コア率は最終散布径、攻撃力順位の対象は開始時の基礎ATK、バースト時間は10秒・再充填待ちは2秒で固定。マスト3の倍数指定は発動候補制限として扱いますが、その特殊スキルの完全再現ではありません。周期ルール設定は概算では通常オート、CPU詳細で既存ルールを適用します。発動順序・射撃の端数フレーム・同時ヒットの扱いも既存エンジンとは一致を保証しません。

残した候補について、CPU詳細との平均・最大相対誤差も表示します。これは除いた候補の精度を示しません。常時バフは準備時にまとめ、戦闘中の毎フレーム集計を省いています。オバロの項目別量子化などの細部は概算です。

画面には候補数・デバイス名・GPUカーネル時間・転送込み時間・CPU準備等を含む全体時間を表示します。RTX 3070 Tiで同じデモ編成800件を180秒計算した試験では、カーネル約0.7秒・準備転送込み約3秒でした。初期化済みのプロセスでの値で、CPU詳細と精度が異なるため高速化率の比較には使えません。実際の編成・効果数で変わります。

追加のCUDA ToolkitやPyTorchは実行時に不要です。`app/combat.ptx` と `app/disjoint.ptx` をインストール済みNVIDIAドライバーで実行します。専用プロセスがCUDAコンテキストを保持し、サーバー終了時・GPU処理中キャンセル時は終了します。GPU実行失敗時は理由を表示し、CPUの候補順・詳細計算へ戻ります。Intel/AMD用バックエンドは未実装です。

CUDAソースを変更した場合のみ、NVIDIA CUDA ToolkitのNVRTCを使って `python scripts/build-combat.py` でPTXを再生成します。[NVIDIA NVRTC](https://docs.nvidia.com/cuda/nvrtc/) のPTX生成APIを使用します。通常の起動・探索ではコンパイラーを呼びません。`python scripts/benchmark-combat.py --candidates 800` で同じデモ負荷の計測を再実行できます。

## BlaBlaLink取り込み

「所持・育成データ」にプロフィールURL入力欄と、書き出し用ブックマークを用意しています。URLを貼ってプロフィールを開き、登録したブックマークを自分のログイン済みBlaBlaLinkタブで実行します。URLを貼るだけではBlaBlaLinkの認証された育成情報を取得できません。

現在のプロフィールURLの `openid` は `29080-...` をBase64化した値です。公式フロントエンドはこれを復号し、さらに `29080-` を取り除いた数字部分を `intl_open_id` に入れます。今回これに合わせました。初版は復号がなく、前版は接頭辞の除去が欠けていました。応答1301000だけで認証・公開範囲の問題とは断定できません。**古いブックマークを使い続けず、「育成データを読み込む v3」から再登録してください。**

取得後、同じPCの計算ツールを開いて `postMessage` で取り込みます。受信側はBlaBlaLinkのオリジン・送信ウィンドウ・ランダムな一時IDを検証します。ログインCookieやパスワードはコピー・保存・送信しません。ポップアップ制限・接続不可・自動取り込み失敗時はJSON保存へ切り替えます。ブックマークのID変換と取得・JSON化はモックAPIで検証済みです。今回の自動ブラウザ操作では `javascript:` の実行がセキュリティポリシーで拒否されたため、実アカウントの最終取得は未検証です。

入力に対応する形式：

- 本ツールが書き出す `nikke-tools-blablalink-v1`、または `characters` / `details` / `state_effects` / `outpost` の原始JSON。
- nikke-calcの育成プロファイル（`chars` / `_account`）。名前はエンジンの韓国語正式名です。画面はIDで対応した日本語名を表示します。
- 本ツールから書き出した `nikke-tools-session-v1`。

未知のキャラ・オバロ・宝もの、詳細未取得、研究やキューブの不足は表示します。計算対象の不足情報は補完が必要です。データのない項目を強い育成の既定値で埋めません。キューブ未装着は明示的に対応しています。キューブの装着情報は所持一覧全体を証明しません。

オフライン変換に使うID・宝もの対応表は `data/import-mappings.json` です。更新する場合は `scripts/prepare_metadata.py` の標準出力をこのファイルへ保存します。このスクリプトが取得するのは公開マスターデータだけです。

## 詳細GPU版の実装・CPU照合

v35ではHP閾値の下向き通過、指定した到達回数、部隊の味方HP・隣接HPの通知、隣接キャラの満タン復帰をGPU内で処理します。HP消費・被弾・回復・最大HPの変化ごとに、その場で通知を処理してから次の対象へ進みます。発動中に回復した場合の再入防止、部隊順と登録順、同じ閾値の重複、1e-6の境界判定、復活中に余分な閾値通知を出さない規則も固定CPU版に合わせています。HP閾値通知と同じ文字列の明示的な通知は別のイベントとして扱います。

ネイティブ版とPTX版の両方で、基本24件・通知名の区別3件・実スキル部隊12件の計39件を照合しました。部隊合計と5人のダメージ、バースト履歴、乱数状態、HP・遮蔽物HPの各フレーム、最終の弾数・チャージ・戦闘不能状態を比較しています。整数結果と通知順序は一致、HP等は相対1e-12／絶対1e-6の許容差で確認しています。A2のBモード解除、ソリン：フロストチケットの回数判定、フローラの中央・両端の配置を含みます。通常経路の95テストと、通常API・ブラウザーのGPU単独／CPU照合付き計算も成功しています。記録は `research/detail-hp-edge-checkpoint.json`、再現用の架空データは `research/detail-hp-edge-ui-fixture.json` です。

現在のコンパイル対象は203体中150体、愛用品の812条件中589条件です。新たにA2が通り、これまでコンパイルできていた味方・隣接HP通知も、今回の戦闘テストで発動を確認しています。この件数は全キャラ・全編成の戦闘一致を意味しません。失ったHPへの比例、遮蔽物の復活・一部の制御、回復超過分の蓄積、敵のデバフ・継続被弾、座標などには未対応条件が残ります。実アカウントからの取得成功や高速化率を保証する検証ではありません。

## 探索の範囲と保存

育成逆算は固定編成・1変数の有界全列挙（最大32候補）です。「どの項目を上げるか比較」ではスキル3種を現在Lvから10まで、仮ATK/HP/DEFを現在の加算値から0・5,000・10,000・20,000増やして個別に試します（最大42候補）。複数の項目を同時に変える組み合わせ探索や項目間の費用比較は行いません。候補が単調に強くなるとは仮定しません。「到達」は `>=`、「比較基準を超える」は表示単位で省略しないエンジンの整数ダメージに対する `>` です。最小という表示は指定した離散範囲内だけを意味し、最安の育成コストを示しません。

オバロ合計値の自由指定や基礎ATK/HP/DEF加算は数値実験です。ゲーム内で実現できる装備構成・再抽選費用を保証しません。基礎ステータス加算は戦闘中の攻撃力バフとは異なります。

5部隊探索は、所持・育成と除外条件をもとに、取得元の回帰用編成例と簡易スコアから最大160候補（GPU概算選択時は800候補）を生成し、20 / 80 / 160候補を詳細計算して、重複しない5部隊の合計をビーム探索で選びます。ユニオンレイドでは1部隊を選び、採用時に使用済みへ追加できます。情報不足や未対応の候補は除外し、その件数・エラーを表示します。固定の候補群内の推薦であり、全組み合わせの最適解ではありません。配置・バースト順を別に最適化する処理はまだありません。

「詳細まで続ける」「長時間まで続ける」で、計算済みの候補を引き継げます。途中までに見つけた最良の推薦は保持し、探索量を増やしても合計ダメージが下がらないようにします。GPU詳細計算では候補を最大32件ずつまとめ、同じ実行スケジュールの部隊を並列に計算します。編成ごとの状態・乱数・結果は独立です。一時停止は実行中の一括計算を終えて1件を反映したところで止め、残りの計算済み結果は再開時に再利用します。再開と計算キャッシュは現在のサーバープロセス内で有効です。サーバー再起動をまたぐ途中位置の再開は未対応です。

「保存・書き出し」は原本・補完・検討案・比較基準・計算履歴をJSONで保存します。個人の育成情報を含みます。再取り込みで設定を復元できますが、探索ジョブは新しく開始します。5部隊の長時間探索はブラウザを閉じてもサーバーが起動している間は継続するため、終了ボタンで止めてから終了してください。

## 候補探索の速度改善

通常画面の比較・育成逆算・部隊探索は、単体と一括で入力準備・GPU実行・結果復元を共用します。実行時間やボスの予定が異なる候補は、命令列の一致でグループを分けます。未対応効果のCPU計算、任意のCPU照合、結果の順序、終了・再開は同じ境界で処理します。

RTX 3070 Tiの通常APIで、キャッシュを使わない8候補が35.17秒から4.81秒（約7.31倍）になりました。変更前と全候補のダメージ・メンバー・バースト履歴などが一致しています。測定記録は `research/performance-api-before.json` と `research/performance-api-after.json` です。1部隊の計算時間を短縮した値ではなく、GPUや編成、戦闘時間、CPU照合で効果は変わります。CUDAの戦闘処理とバイナリは変更していません。

`compute.elapsed_ms` は入力の梱包・メモリー確保・転送・GPU実行・読み戻しを含むグループの実測時間です。複数候補へ同じ時間を表示します。`amortized_elapsed_ms` は候補数で割った参考値で、1候補の待ち時間ではありません。`workspace_bytes` は部隊単位、`batch_workspace_bytes` はグループ全体を示します。

GPU内のイベント処理も、全効果の走査から、イベントに関係する効果の順序付き一覧へ変更しました。キャラ名による分岐は追加していません。RTX 3070 Tiのキャッシュなし通常API測定で、8候補が4.63秒から3.40秒（約1.36倍）、対象別カウンターを含む90秒戦闘の8候補が20.20秒から13.36秒（約1.51倍）になりました。変更前後で全候補のダメージ・メンバー・バースト履歴などが一致しています。これは各条件での1回の比較測定で、全編成に同じ倍率を保証しません。記録は `research/event-index-control-after.json` と `research/event-index-counter-after.json` にあります。

`compute.timings_ms` には、GPUカーネルをCUDAイベントで測った時間と、準備・転送・読み戻し・復元の時間を分けて記録します。複数候補の場合はグループ全体の値です。仕組みと共通パターンによる検証方針は [イベント実行の索引](docs/event-dispatch-index.md) を参照してください。

召喚物の個別の期限・生存数による攻撃間隔・再召喚を扱う [共通の周期リソース](docs/periodic-sources.md) を追加しました。アインのフェザーもこの処理を使います。取得元の寿命と間隔は推定値のため、CPU・GPUの両方で注意を表示します。標準条件で入力変換が通るキャラは182/203ですが、全編成やゲーム内実測との一致を意味しません。新しい同種の効果は、キャラ名による計算分岐を追加せず、名前と枠ごとの期限・間隔をデータで指定できます。
