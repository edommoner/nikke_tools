# 現在の最大装弾数による倍率の正本契約

共通CLIの `reference --suite max-ammo-scaling --out <new.json>` に正本20契約を追加した。GPU/packing禁止の既存reference実行経路を再利用する。CUDA/Metalの本体へ接続する前のCPU契約であり、GPUの受付は拒否したままである。

## 数値と照会時点

正本はBuffManager.get_buffsで対象の所属・条件・stackを評価し、_get_valueの戻り値に_scale_by_max_ammoを適用する。付与者の容量や付与時snapshotではなく、actual_recipientの照会時点のCharState._full_ammoを使う。最終的な値はstack反映後の値×整数容量。percentageを再び100で割らない。

通常武器はbase + 各割合グループを0.5切上げした増加量 + 固定加算の偶数丸め、下限1。base5に別グループ10%を2個なら7発、同一equipment groupへまとめると6発、50%なら8発、flat2.5なら7発となる。負の最大装弾数増加は下限1へ丸める。

武器変更の固定max_ammoは装弾数buffを無視する。max_ammo_buff_applies付きはモード容量を基準に計算するが、_wc_ammo_fullは再装填まで固定する。late-flatが.4秒に有効になっても2発のmemoを保持し、再装填時.7666666666666674秒に6発へ変わる。モード失効後は通常武器のlive容量へ戻る。1発持続の倍率は付与した弾の容量を保存せず、効果を受ける発射時の容量を読む。

## 再帰と観測

_full_ammoは再びget_buffsを呼ぶ。同じrecipientが_ammo_queryにいる内側ではscaled buffをNoneとして省略する。provider欠如・戻りNoneも省略。例外時でもfinallyでguardを解除する。スキップと倍率0は異なる。

world_max_ammo_scaling_nativeは実際の_scale_by_max_ammoのcall/returnと、登録済providerへ戻る_full_ammoのreturnだけをprofileで観測する。追加get_buffs/provider照会は行わない。20戦闘で外側1349照会、内側1170省略を記録。モード固定容量では内側get_buffsを呼ばないため、常に1対1の再帰にはならない。観測前後で全native field・skill trace・RNG・物理packetが等しく、buff照会と弾数消費の呼出数も変わらない。

## 共通実行器へ接続する際の設計

canonical compilerは既にMAX_AMMO_SCALE=-4を保持している。正本やlegacy compilerを書き換えず、private portable hostでその量源を区別し、共有Slangのnumeric lookupへ接続する。名前付きstack referenceやduration referenceと混同しない。Runtimeの一律大型化を避け、既存fullCapacity/ammoInstantCapacityの丸め・mode epoch/magazineを再利用する。公開入口と不正な量源・stat・非combat/worldの拒否を維持する。

collectStats内のrecipientValue直後が倍率の候補位置だが、単純にammoInstantCapacityを呼ぶだけでは設計完了ではない。ensureNativeNumericとの循環、内側のqueryActive/target/late rank状態の復帰、dictionary cacheへ未完成の値を登録しないことを確認する必要がある。同じrecipientだけをguardし、別recipientの有効な照会を抑制しない。異なる武器snapshotやmode latchを現在ammo残数に置き換えない。

次はこの20契約を同一CUDA/Metal入力表へ接続し、拒否入力と旧321のbyte保持を検証する。さらに原エミリアの全定義3秒/30秒を改変せず実行し、親割合damageと1発容量倍率の同居を確認する。late rankやtarget混在を未検証のまま全面対応と認定しない。Windowsは現CUDAで必要な短い検証だけに限定する。
