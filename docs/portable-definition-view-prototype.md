# 次のcompiler仮説：Definitionの一括実体化を避ける

v134はcommands単独の5.46MB PTXでも2GiB内のassemblyに失敗した。追加のinit/write試行、別option、RDC等の自動fallbackは行わない。保存PTXのCPU解析は191関数、最大virtual宣言5,328（basicConditions）、最大local宣言8,488byte（dispatch）。Frameは32要素で、宣言上の1要素scalar layout推定104byte。これらはcompilerメモリ原因を特定する証拠ではなく、Frameの常駐化を即採用する根拠にもしない。根拠はresearch/portable-world-v134-saved-compiler-analysis.json。

一方、現在のDefinitionはimmutable inputの55項目をnoinline loadDefinitionで毎回デコードする。生成CUDA上のscalar layout推定は248byte。readDefinition／residentDefinitionはこの記録を値として扱う。宣言サイズだけからcompiler必要メモリを換算しないが、巨大な記録の一括コピーを避ける別の表現を安く試す理由にはなる。

## Macの一時プロトタイプ

本worktreeを変更せず、共有source closureを新しい/tmpへ複製した。Definitionをwire input/row、ローカルoverride mask、2つのoverride値の計5uintへ置き換え、各propertyから元のdefinition_* accessorを呼ぶ。実際の代入があるdamageRoute／damageHitsだけはsetterでローカルoverrideを保持し、inputを書き換えない。読み取りだけの53項目はgetterとする。一般的なget/set propertyの構文は[Slang公式資料](https://docs.shader-slang.org/en/stable/external/slang/docs/user-guide/03-convenience-features.html)に基づき、内部機能のref accessorは使わない。

修正は一時コピーのevent_runtime.slangのDefinition宣言とdefinition_runtime.slangのloadDefinition本体だけ。全数値式・event/weaponの本文・getterのwire offset・Runtime layout・normalizerは変更していない。元worktreeのsource SHAが前後同じことも確認した。

通常propertyのv2とForceInline accessorのv3は、同じ共有builderでCUDA／Metal生成に成功した。Definitionの生成宣言は5項目／20byte推定となったが、CUDA生成量は元1,202,619byteに対しv2が1,271,323、v3が1,274,125へ増えた。関数もv2で573→619、noinline190は不変。記録を小さくしただけでcompilerメモリ改善とは言えず、何度もwireを読むことによるGPU負荷増も未測定。getterをForceInlineにしてもCUDA字句量は減らず、v3を優位と認定しない。元の/tmp path別名による初回source生成前エラーも保持している。

正本はresearch/portable-definition-view-prototype.json。生成物とscriptは記録内の/tmp pathに保持する。両案ともSlang生成だけで、Metal実行・NVRTC・ptxas・driver・GPU0。数値一致・実ABI・性能・compiler成立は未検証で、本番実装へ入れていない。

通常property案の再現scriptはresearch/prototype-definition-view.pyへ保存した。Macで`python research/prototype-definition-view.py --out <fresh-directory>`を使い、既存共有builderだけで一時コピーを生成する。元sourceを変更せず、Windowsでは起動を拒否する。記録したscriptによる再現でもCUDA／Metalのbyte数とSHAはv2と全て同じだった。生成失敗はreportとともに非ゼロ終了し、既存出力先は置換しない。

## 次に必要な判定

wireがdispatch中に不変であること、row/inputのsnapshot、copy時のoverride値、2種類のローカル書換え8箇所、signed／binary64を含む55項目の元accessorとの対応を契約で検査する。これが成立してから一方を実装候補とし、fresh immutable packageの全CPUとMetal796/native633・全raw保持・独立sealを通す。巨大なDefinition値を減らす仮説として検証し、source bytesの増減を成功条件や必要メモリの推定にしない。CPU契約やMetalで差が出れば、原失敗を保持して候補を修正する。

現在のWindows候補v134は終了済みで、追加compiler実行は依頼していない。前後観測の欠落7件・service unverifiedはpreservation=falseのまま。全キャラ認定0、full796 CUDA未成立、回復分配28件はCPU契約まで。
