# 最大HPから攻撃力へ変換する効果の接続設計（未実装）

`atk_from_hp_pct` はGPU受付をまだ有効にしていません。次の効果群のCPU調査であり、現在の固定ソース `20e213b` の計算・検証には影響しません。

`research/characterize-atk-from-hp.py` は元BuffManagerで60条件を検証しました。全5所有者、自己／全味方、負・ゼロ・正の割合、無限／有限期間について、5受領者×4時点を観測しています。受領者の最大HP変化は即時に反映され、現在HPだけを1にしても攻撃増加量は変わりません。有限期間の効果も付与時のHPを固定しません。この調査はダメージ・実戦・GPUの認証を含みません。

元CPUの式は `recipient_final_max_hp * (value / 100)` です。除算を先に行うbinary64順序を共通数値演算で保持します。通常の `atk_flat` 集計後、HP由来の各項を順番に加え、その後にキャスター基準の各攻撃項を加えます。後者を既存の通常走査で先に足している実装へ単純な分岐追加をすると、混在入力の丸め順序が変わり得ます。旧入力の全出力保持と、桁差・打ち消しを含む混合ケースが必要です。

旧コンパイラーはこの効果をkind4・HP用フラグ241で表現しますが、共通実行器のkind4はバースト段階上書きです。BUFFSへの名前追加だけでは受付しません。専用の共通識別子と明示的な翻訳・生入力検査が必要です。既存64要素の数値配列へ無条件に添字を追加せず、元効果との衝突を検査します。

無限効果の未解決対象は、この後処理では元CPUが `_resolve_target` を新たに呼びます。通常の遅延対象キャッシュをそのまま使うと順位対象の意味が変わります。さらに `effective_max_hp` の条件再検査には既知のCPU差分があり、実行時条件付きHPのGPU契約を変えるかどうかは、独立した入力と元CPU観測で判断します。既存のベクハク2固定条件の差分例外を他の効果へ広げません。

次に必要なのは、通常flat／HP変換／キャスター基準flatの混合順序、重複・スタック・期限、実行時条件、順位対象、最大HPの各供給源、ダメージ実行と対象選択への伝播の元CPU観測です。その後に共通Slangへの接続、共通fixtureと拒否ケース、Metalの比較前readback保存、既存全入力の比較、必要な短いCUDA実行を行います。全キャラ認証は0/203のままです。

追加の `characterize-atk-from-hp-order.py` は60条件（全5所有者×全6登録順×自己／全味方）で、HP由来の +1e16／-1e16 を相殺した後にキャスター由来1を加えると、どの登録順でもflatが1になることを確認しました。効果全体の登録順で混在加算すると一部の順序で0になり得ます。元の順位用 `_effective_atk` はHP由来を集計せず、この入力では1001でした。順位へHP由来量を追加する実装は元CPUの契約を変えるため行いません。

この追加研究の最初の入力では通常 `atk_flat` 効果が元CPUの `_STAT_TO_BUFF` に存在せず、想定した通常flatは加算されませんでした。GPU差分ではなく研究入力の仮定誤りです。実際に対応するHP二項とキャスター項へ入力を修正し、元の関数や期待値の許容誤差は変更していません。
