# RuntimeのGPU常駐参照を検討するためのコード生成実証

CUDA11.3のv115に続き、依存ロードを修正したNVRTC12.4.127のv120もCUBIN O1を生成できませんでした。v120は42.402秒、NVRTC30.859秒、return6／ptxas allocation failure、Job peak2,148,052,992byte、2GiB上限・post空・retry0です。primaryとbuiltinsの実ロード、nvrtcCreateProgram成功は確認されています。版変更だけでは既存上限内のcompiler成立を解決できていません。上限との因果や内部の最大消費関数までは未証明です。

次は同じnoinline追加や少数配列の機械的移動を繰り返さず、Runtime全体をGPU常駐バッファ上の参照として渡す一つの構造仮説を調べます。数値・状態・効果の計算本体は共通Slangのままです。CPUが時刻・対象・中間状態を代行する経路は作りません。

## 小さいプローブで確認できたこと

`gpu/runtime_storage_probe.slang`に512要素のuint／uint64配列を持つ構造体と2方式を用意しました。一方はRWStructuredBufferの要素をinout引数へ渡し、もう一方はlane番号から直接要素を更新します。laneごとに独立したcontrolを使います。

`.venv/bin/python research/probe-runtime-storage.py --out <新規JSON>`は既存portable_backend.buildを使い、2 entry×CUDA／Metalの4生成を検査します。GPU execute／execute_batchesは禁止し、NVRTC・Metal pipeline・GPUは実行しません。出力の構造体ポインターとprivate構造体copy宣言の有無を確認し、source／generated SHAを記録します。

現Slangではinout方式も、CUDAはresident要素へのポインター、Metalはdevice ProbeStateへのポインターへ変換され、private ProbeStateの宣言を生成しませんでした。関数引数もlane/indexに特殊化されています。結果はresearch/portable-runtime-storage-codegen-proof.jsonです。これは小さい例の生成テキスト確認であり、実Runtime、物理ABI、ptxas peak、Metal pipeline成立、性能、戦闘計算一致の証明ではありません。

## 本体候補を作る前の条件

1. 全Runtimeの参照経路を調べ、値渡し・local copy・別programとのaliasを起こす箇所を洗い出す。FrameのDFS配列など残るprivate状態は別に扱う。
2. 既存entry本体を共有helperへ分け、GPU上のRuntime要素をinoutへ渡す候補を作る。入力効果・実行順・全readbackの契約は変えない。通常の既存entryを比較基準として保持する。
3. 追加のscratch bufferをCUDA／Metalの転送ABIへ明示する。推定138,928byteを物理sizeofと断定せず、layout／stride／binding／program数との対応を確認する。初期化もGPUで既存initializeRuntimeを使う。
4. 小さい独立実行でbinding・複数lane・境界を確認してから、immutable候補のMetal759と保存baselineの全raw／native保持を検査する。比較項目・拒否・normalizerを緩めない。
5. 本体の実コード生成にprivate Runtimeの除去を確認でき、Metalが通った場合だけ、Windowsで60秒／2GiB以内のcompiler-only1回を選ぶ。小さいプローブの成功だけでWindowsへ追加試験しない。

compiler／cache／数値の成否は分けます。v120に成功artifactがないためwarm cacheは未検証です。v119の依存失敗も保持しています。通常UI CPU、全キャラGPU認定0、最新版CUDA計算一致未確認、entry_reloadはCPU32契約まででGPU未対応、最終目標未完了です。
