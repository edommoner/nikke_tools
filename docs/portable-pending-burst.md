# 共通GPUのB3予約ダメージ

ABI `0x50455645`。CUDA/MSLは同じSlangから生成し、予約の状態・入力・期待値・CPU参照も共有します。入力と出力は各53,248語、同時予約512件、定義256件です。全キャラ・全変種の認証は引き続き0/203体で、通常画面への接続は未完了です。

## 捕捉・計算・着弾の順序

元からB3であるキャラの、timingに `burst_cast` を含む **plain `bonus_damage`** は、効果が発動した時点で係数と時刻・反復数を予約します。実効バースト段階を変更しても、この判定は元のB3属性です。B1/B2、`bonus_damage:3` 等の明示的な反復付きstatは通常経路のままです。係数0は予約せず、条件と発動予算は予約時に判定し、着弾時には再判定しません。予約された追加ダメージの係数へ、周期登録のDoT用stack倍率を掛けません。

フルバースト開始では、全員の開始通知とCDの追加反映を終えた後、全予約のダメージを先に計算し、その後に着弾します。係数以外のバフは開始時点から読みます。計算基準の防御はCPUと同じ本体です。着弾先は着弾時の生存者と照準から共通の敵処理が選び、ADDのHPクリップ・本体／ADD／過剰分の集計を再利用します。再突入で複数回発動した予約を保持し、全件の着弾が終わるとキューを空にします。

## 後続バフの除外

同じ発動者の、ダメージ効果より後ろに記述された `burst_cast` buffの名前を静的に求めます。該当する名前を持つ、その発動者の全buff定義をbitmaskにし、予約ダメージのバフ辞書を作る際に除外します。同名でも別の発動者が付けたbuffは残ります。この除外は通常の射撃・CD・回復・対象順位の評価へ持ち越しません。遅延対象も、除外判定の後で解決します。名前のない後続buffは除外集合へ入りません。

`same_target`、`enemy`、`target_body` はCPUの照準先に対応します。`same_target:参照名` の追加ダメージは、同じ発動者の一意な直接攻撃を静的に参照します。予約時だけ、その参照先の正の整数反復数を使います。通常経路のB1/B2は参照先の反復数を追加しません。動的な回数、複数の参照候補、他の発動者の参照、周期ランプは拒否します。

元のB3予約経路は、一般スキルの名前付き命中通知とゲージ加算を発生させません。この違いを期待値に含め、後続の予約が命中子イベントで強化される誤りを防ぎます。予約と各着弾の時刻、係数・反復数、保持／投入／処理件数を共通出力で確認できます。

## 証拠と残る範囲

`portable-pending-burst.json` の27ケースを独立期待値として使い、CPUの実BurstController `_fire_pending_burst_dmg`、BuffManager、数式、BossScriptの部品へ照合します。これは敵パターンを含むCPU戦闘全体の認証とは別です。512予約の保持・一括flush、満杯時の拒否、ログ上限、静的maskの所有者・定義範囲も検証します。

元のドレイク編成4条件に、ミランダ・ドラー・ブリッド・N102・メアリーの3・30・180秒とSR15育成180秒を追加しました。全効果を省略せず、計8条件についてCPU戦闘本体と各人ダメージ・全バースト時刻・HP・遮蔽物・有効な武器待ちが一致しました。固定版 `51fe398` はWindowsのRTX 3070 Tiでも低優先度・1回、29.728秒で522正例・51拒否が成功しました。共通ソース・入力・全出力・検証コード・全status・全CPU参照リストがMetalと一致し、生成CUDA/MSLも改行・位置情報・標準includeパスだけの正規化で一致しました。元のWindows作業状態を保持し、残存プロセス0です。モデル混雑で中断した要約転送は既存ファイルから再開し、GPU計算を繰り返していません。 最新の確定結果と効率化は `research/portable-combat-checkpoint.json` を参照してください。

明示的な `land_in_full_burst`、動的stack係数、複数受領者の周期時計、敵の座標・部位・保護層、手動操作等は引き続き接続が必要です。入力preflightを全キャラのGPU対応件数へ加算せず、[全体の完了条件](portable-roadmap.md)を維持します。

## 効率化

全予約の計算中はイベントを発生させず、対象のHP更新も後段です。隣り合う同じ定義・同じ捕捉係数の予約は、計算済みの値を再利用します。16入力×512予約の固定負荷を3回ずつ測定し、入力・全出力を一致させたままGPU中央値が28.076msから21.122msへ約24.8%短縮しました。`PORTABLE_PENDING_RECALCULATE_REFERENCE` は同じ共通実装で再計算を強制する比較用フラグです。これは予約計算の測定であり、実編成全体の性能やメモリを証明しません。証跡は `portable-pending-benchmark-{before,after}.json` です。

## Metalのコンパイル競合

最終回帰を6処理同時に起動した際、4つのSwift起動がpipeline compileの120秒上限に達し、APIも応答待ちでタイムアウトしました。同じソースの実編成8条件と、その後の単独573入力は成功しており、GPU計算へ入る前の競合です。失敗は `portable-pending-concurrent-compile-timeout.json` に保持しています。

輸送用Swiftでlibrary/pipelineの作成だけをプロセス間のadvisory lockで直列化しました。GPU命令の作成・転送・実行へ進む前にロックを解放します。意図的に親が保持したロックを子が待ち、解放後に実Metal計算と既存期待値が成功することを `verify-portable-metal-lock.py` で検証しました。その後、同じ並行条件で共通573入力・実編成8条件・203武器／装備・旧イベント・HTTP API・34,874数値ケースが成功しました。待ち時間は `pipeline_lock_wait_seconds` として記録します。待機を含むSwift起動の120秒上限は保持し、タイムアウト後の観測だけを理由に処理を重複起動しません。
