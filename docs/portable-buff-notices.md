# 名前付きバフの同期通知

共通Slang実行器でバフ本体を登録してから、名前付き通知を同期実行し、最後にHP付与を処理します。CUDA／Metal専用の効果実装は作りません。

固定CPU本体の `_activate` と `_event_audience` の規約は次のとおりです。

- 新規登録は名前通知を全受信者へ完了してから、シールド等の別処理に先立ち、発動者へ `stack_reach:name:1` を送ります。
- 重ね掛け可能なバフの更新は、スタック数が変わった場合にスタック通知を完了してから名前通知を送ります。上限に達しても名前通知は送り、最大1スタックの単純更新では名前通知を送りません。
- 既定の名前通知は部隊順です。`event_scope: recipients` は実際の受領者とその順序に限定します。確定した対象0人には通知せず、遅延解決で対象が未確定なら発動者へ送ります。
- 名前がないバフは名前通知・スタック通知を送りません。スタック通知の対象は発動者で、名前通知の受領者指定とは別です。
- 通知は登録直後の状態を参照できます。子の通知を終えてから次の受信者へ進みます。名前通知やスタック通知による取消・再登録を処理してから、まだ残るバフを探してHP付与を計算します。

論理イベントを明示スタックの継続フレームで処理します。名前通知の受領者順はGPUで解決し、遅延対象の解決後も保持します。入力は静的な定義と刺激だけで、CPUの途中状態・対象・発射予定を渡しません。

対象は既に受付済みのバフ種別です。シールド・分身など、未移植のバフ本体の受付をこの通知接続だけで開きません。通常画面のMetal接続と全203体の全効果・全条件の検証は未完了です。

## 検証結果

固定版 `7977cc6` は、Metalで686正例・74拒否、名前付きバフの独立CPU参照22件、単体41件が成功しました。新規22件は受信順、新規／更新／上限更新、最大1スタック更新、空の対象と未解決の対象、遅延対象の解決後の順序、同名統合、入れ子の自己更新、取消後のHP付与中止を含みます。新規ケースでは宣言された例外を設けず、HP・状態をCPU本体と厳密に照合します。従来のモード境界の既知差異1件は引き続き別記録です。

WindowsのRTX 3070 Tiでも低優先度・120秒上限の1回だけ実行し、44.736秒で成功しました。両GPUの共通ソース、入力・全出力、検証コード、全ステータス・ケース・既知差異・全CPU参照リストが一致し、生成CUDA/MSLも改行・位置情報・標準includeパスだけの正規化で一致しました。Windowsの元の作業状態と既存GPUサービスを保持し、検証用プロセスは終了しています。要約は `research/windows-portable-combat-v26.json`、生成比較は `research/portable-generated-v26-comparison.json` です。

Metalでは全入力候補17体を含む通常／SR15の180秒・34実編成、固定8実編成、203武器、203部隊の装備初期化、既存16イベントと2拒否、HTTP経路の新規代表5ケースを含む回帰検証も成功しました。数値コア34,874件は成功証跡の依存ハッシュが現在も一致しています。

通知先が存在し得ない場合、通知対象の解決を省きます。固定負荷は16入力・256バフ・各21回の発動、受領者限定・名前通知の受信者なしです。他の本チャットの検証終了後、通知先を毎回計算する版と省略版を各3回単独測定し、入力・全出力のハッシュが一致しました。中央値は70.440msから67.641msでしたが、試行範囲が重なるため約4%の差は参考値であり、安定した速度向上や実編成全体の性能を証明しません。

最初の実装で関数追加時に `dispatch` のインライン抑制指定が外れ、Metalパイプラインのコンパイルが120秒上限に達しました。指定を復旧し、武器フレーム本体にも抑制を戻した共通ソースで両GPU検証を完了しました。失敗証跡も `portable-buff-notices-{pipeline,factored}-timeout.json` に保持しています。
