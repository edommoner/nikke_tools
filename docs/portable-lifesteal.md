# 吸血回復と着弾フェーズ（作業中）

安定版はABI `0x50455656` の段階索引までです。ここに記載する吸血は通常弾経路の試作で、`lifesteal_pct` の製品ホスト受付は閉じています。全キャラ対応や吸血ファミリー全体の完了を示しません。Windowsでこの試作は実行していません。

## 確認した契約

計算は共通Slangで、`damage * rate / 100 * (received * outgoing)` のbinary64演算順を維持します。回復元は攻撃した本人です。味方から付与された吸血について他者回復として扱うかは元CPUにも実機未確認の注記があり、受付を開く際はモデル警告を維持します。正の吸血率は満タン・回復倍率0・丸めでHPが増えない場合も回復通知を送り、非正の率は送りません。初期HP0はダウン通知と別で、明示的な致死被弾後のダウンは回復しません。

CPU参照は、互換層を適用した元の `timeline.simulate` 内の `_apply_lifesteal` コードを呼びます。式をテスト側へ書き直していません。通常射撃は実際の `CharState.tick` が返したパケットへ適用します。GPUは通常弾の射撃・命中・最終弾・モード終了通知を終えた後、捕捉した各物理命中の量で回復します。通常弾・割合・回復倍率・満タン・通知・致死被弾を含む15ケースがApple M5のMetalでCPU参照と一致しました。`research/portable-lifesteal-focused-metal.json` はホスト受付を迂回した試作wireだけの実証です。

## 未接続を実測したケース

実際のCPU `timeline.simulate` を、静的な5人・1射手・攻撃時に2ヒットのスキル・吸血5%・HP100/1000・攻撃1000という入力で実行しました。射撃直後の通常弾は時刻0で50回復し、攻撃時スキルの2ヒットは次のフレームの着弾処理で各50回復します。最終HPは250、総ダメージは3000です。現試作のGPUは総ダメージ3000ですがHP150で、スキル着弾の回復が未接続です。差は `research/portable-lifesteal-landing-phase-study.json` に `passed: false` のまま保存しています。CPUで作った状態・着弾予定表をGPUへ渡していません。

## 次の実装条件

- スキルの量は活性化時に捕捉し、命中数・名前付き通知・ゲージを元の順序で処理する。吸血通知が親の捕捉済みスキル量を再計算しないようにする。
- GPU内の共通着弾キューは、周期／DoT収集後、バースト前のフェーズで元CPUと同じ順序に排出する。通常弾から生成したスキルは次フレームへ保持する。
- 排出中に子の回復通知が同じキューへ追加した着弾も、Pythonのリスト反復と同じ順序で扱う。明示的な仕事量上限を持つ。
- B3保留パケットは全量を先に算出してから着弾する。回復通知中に追加された次の保留を親のキュー消去で失わないようにする。
- 各敵への配分・丸め後の量で回復する。敵の消失、死亡、再出現世代、固定された物理弾と複数対象の順序を検証する。
- HP率の同期と境界通知を回復通知より先に完了し、自分由来の回復判定・出力の実回復量・次のパケットの読み取りを照合する。
- 自律戦闘の本体タイムラインと、外部刺激で部品を検査する経路を区別する。部品実証だけで実編成や通常画面を認証しない。

この回帰が成功し、全経路・既存回帰・両GPUの短い照合を終えるまで、製品の吸血受付や全キャラ認証を広げません。

試作のfixtureと検証ロジックは両バックエンド共通です。Metalでは `.venv/bin/python research/verify-portable-lifesteal-prototype.py --backend metal`、着弾差の再現は `.venv/bin/python research/study-portable-lifesteal-landing.py --backend metal` です。同じスクリプトは `--backend cuda` も受け付けますが、この試作のWindows実行は未実施です。
