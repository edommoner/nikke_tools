# 武器モードの開始通知と物理セッション

武器変更・散弾・バースト再突入は共通のSlang実行器で処理し、CUDA／MSLを同じソースから生成します。武器モードの開始・更新は、論理状態を先に設置してから、捕捉した名前で部隊の0〜4番へ同期通知します。各受信者の子イベントが終了してから次の受信者へ進みます。途中のキャンセルや別モード開始でも親通知の名前と残りの受信順を保持します。名前のないモード、トグル解除では開始通知を発生させません。重複したトリガー記述の発動回数は保持します。

論理的なモード登録と実際の武器への移行を区別します。物理移行前に開始通知から取り消されたモードは、元の弾倉、装填、チャージ、射撃スケジュールを変更しません。通常武器の射撃コールバック内で登録・取消が完結した場合も、その射撃の消費と後続スケジュールを完了します。実際に別セッションへ移った場合は新セッションを保持します。

`portable-mode-sessions.json` の15ケースは、部隊通知、状態の先行設置、更新、解除、入れ子、受信順、有限の再帰、未移行キャンセル、射撃／最終弾／フルチャージ中の一時的な変更を扱います。CPU参照では元のBuffManager、BurstController、CharStateを実行し、CPUの途中状態はGPUへ渡しません。キャンセルはネイティブCPUでも実際にモードを解除するトグル操作を使います。`remove_named_buff` のモード解除や重複通知について最初のテスト案が置いた誤った仮定は、`portable-mode-fixture-assumption-audit.json` に保存しています。

## 同一フレームで終了・再開始する境界

固定CPU参照では、期限切れ後の終了通知が同じフレームで子モードを開始すると、`CharState._in_weapon_change` が終了を観測せず、旧弾数・発射数・発射待ちを持ち越します。既存のゲーム仕様記録 `GAMEPLAY.md:577-578` は、武器変更時に専用弾倉と新しいチャージへ移行する規約を記しています。共通実行器は既存の新セッション規約を維持します。新しいゲーム内実験は実施していません。

`portable-mode-session-contract.json` は根拠文書とCPUソースのハッシュ、1ケースの3フィールド差を明示します。共通テストは生のCPU値と手書きのGPU期待値をそれぞれ検査し、宣言していない全CPUフィールドを厳密に照合します。CPUとの差を一括で許容せず、CPU完全一致とも扱いません。

## 検証の範囲

共通コアの武器変更・散弾・再突入テストに加え、今回の開始通知と未移行キャンセルを同じ入力・期待値でMetal／CUDAへ実行します。HTTP経路にも代表5ケースを含めます。深さ上限を超える再帰と不正な名前フラグは拒否します。

`benchmark-portable-mode-entry.py` は、関係のない255定義と1モードを持つ16入力で開始通知の走査を比較します。最適化版と全走査版の全出力を一致させる局所測定であり、実編成全体の性能を示しません。

通常バフの名前付き開始通知と `event_scope`、HP更新と新規／更新通知の順序、さらに広いモード衝突は次の接続対象です。通常画面のMetal接続、全203体の全効果・全条件の検証は未完了です。
