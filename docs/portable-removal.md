# 名前付き状態の除去と終了通知

ABI `0x50455659` のMetal全体カーネルで1092正例・195拒否が成功しました。対象別除去の28件を実CPU参照と照合し、同名の旧1059ケースは全読み戻しが一致しました。新しいWindows固定版の短いCUDA照合、実編成等の残る回帰、効率測定は進行中です。前段の完全な両GPU認証は固定ソース `70f9018`、証跡保存 `272ed61` です。通常画面CPU・全変種認証0/203体を維持し、全キャラ・全特殊効果の目標を継続します。

`remove_scope` の省略／`global` は正確に一致する名前のActiveBuffを、付与者や受領者にかかわらず除去します。`target` は発動時に受領者を解決し、該当するメンバーだけを外します。残りのメンバーがいれば状態・残存時計を維持します。味方の順位・名前付き状態条件・実名、敵の既存共通選択経路を使い、CPUの除去予定表は渡しません。未解決の遅延対象を除去のために確定しません。

名前付きバフの除去は独立した武器変更モードを終了させません。また、ActiveBuffを持たない周期instantの時計は止めません。前段の武器回帰3件と高定義番号の時計1件に誤った期待があり、実際のCPU CharState／BuffManagerを実行して修正しました。以前の期待はfixtureの `corrected_legacy_expectation` と、`research/portable-removal-mode-native-gap.json`／`portable-removal-instant-native-gap.json` に過去の差として残します。

対象の一部を除去しても、発数寿命の対象別カウンターやスタック表はCPUと同様に保持します。終了した状態に紐づくDoT時計は、終了通知の子が再登録するより先に止めます。すべての親状態を変更してから登録順で終了通知を出すため、子が使い直したスロットや新しい時計を親の後処理で消しません。

CPUの敵バフは敵ごとのインスタンスです。GPUでは共通の集合として保持するため、除去された敵の数だけ終了通知を出します。終了通知は出力の既存余白へ16bitで格納し、対象ごとの通知を1件ずつ保持します。私有512ワード配列を廃止し、2048ワードのGPU所有キューで4096通知を保持します。Frameの追加分岐とフィールドを増やさず、従来と同じ排出ループを使います。キュー容量とは別に、1回のdispatchの仕事量には既存の4096ステップ上限があります。入出力strideは増やしません。入力77824ワード、出力90112ワード、着弾2048件を維持します。

`tests/fixtures/portable-removal.json` と `scripts/portable_removal_oracle.py` は両GPU共通です。独立CPU側では元の対象解決・除去・時計を実行し、GPU後の照合にだけ使います。敵インスタンスの集合としてのメンバーと、通知による子の回数を別々に確認します。旧来のCPU capacity observerが比較していなかった時計状態も検査します。現在の定義監査は203体、入力候補29体、未対応ライフサイクル定義93→84件で、全変種認証は0/203体です。

## 初期候補のコンパイル障害と検証メモリ（履歴）

5候補はApple GPUコンパイラー内で `llvm::report_bad_alloc_error` → `SIGABRT` となり、GPU実行に進んでいません。単なる観測タイムアウトとは区別し、各試行の終了コード・ソースhashと、OSのスタック情報を過去の失敗として保存しました。

共通Pythonアダプターの入力・出力は32bit整数配列へ変更しました。非常に長い `struct` 書式のキャッシュとPython整数タプルを避け、little endianのwireを維持します。既存方式で実際のSwiftプロセスへ渡した1287入力と、新しい全入力のSHA256は一致しました。検証中PythonのRSSの観測値は3884800→1696080KiBですが、swapの影響を含む一時点であり、ピーク値やコンパイラー障害の原因を断定する値ではありません。

SDK公開の `MTLLibraryOptimizationLevelSize` も試しましたが、LLVM内の確保失敗は解消しませんでした。この設定は採用せず、既存のdefault最適化と `mathMode=.safe` に戻しています。私有通知配列と追加フレーム分岐を廃止した候補も、全体カーネルの確保失敗は解消していません。GPU所有キュー関数だけの実行は成功しています。GPU実行と数値回帰・両GPU照合が終わるまでは、この候補を認証済みと扱いません。CUDAへ渡す計算本体・効果定義・入力は同じです。

## 定義入力ビューと関数境界

`Runtime.defs[256]` の私有テーブルを削除しました。Slangの構造体配置上は248バイト×256、63488バイトの保存を避けますが、実GPUのピークメモリや速度改善を示す値ではありません。同じwireを読む55個の単項目アクセサーを一箇所に置き、全体デコーダーもそのアクセサーを使います。全体デコーダーはout引数へ書き、小さなビューラッパーだけをinline化します。武器レコードもout引数で受け渡します。数学的な手順は変更しません。

大きな値を返すデコーダーだけの比較版でもAppleコンパイラー障害を再現しました。除去呼び出しを省いた版、通知を私有配列へ戻した版も障害が残りました。定義ビューに加え、入力検査76行を共通のnoinline関数へ分離し、初期化・読み戻しを分割した候補は全体実行に成功しました。この複合変更のどれか一つだけを原因と断定しません。通常のmathMode safe・最適化default・既存時間上限を維持します。

全体のMetal1092正例・195拒否と28件のCPU除去参照は成功しました。旧同名1059ケースの全読み戻しを保持し、4件の旧期待修正をfixture名と履歴に明示しています。入力ビュー55項目×1024行の境界codec、通知容量4096と4097件目の原子的拒否、実編成・API・数値等の各ゲートは別の報告で管理します。単独codecやキュー検査を全体成功の代わりには使いません。

新しい共通処理の効率測定は、全ての検証とWindowsの結果転送が終了してから順番に行います。全キャラ・全特殊効果の目標は未完了です。
