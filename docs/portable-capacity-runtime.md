# 共通実行器の256定義と実データ準備

ABI `0x5045563D` で定義容量を32から256へ拡張しました。共通Slangの定義・受領者mask・時計・カウンター・HP監視・量補正グループ・読み戻しの領域をそろえ、既存コンパイラーの256定義／8語の参照と一致させています。明示イベントスタックの深さ32と、1定義1キャリアの現行モデルは別の制約として残ります。

## wireと参照

入力は45,056語、出力は28,672語です。`app/portable_specs.py` で各領域を整列して配置し、同じ仕様からSlangのschemaを生成します。Swift側は入力の転送上限を65,536語へ増やしただけで、計算・効果参照は置いていません。単一バッチ上限512は定義容量とは別です。

強制スキルの参照は、既存コンパイラーの `B3_MASK` 8語をそのまま梱包し、`index / 32` の語と `index % 32` のビットで読みます。31→32、63→64、127→128、191→192、255の境界、最後の定義から低い定義への参照、同じsource名でも施術者が違う場合の除外を検証します。

時計のqueryには `active_timer_mask_words` を追加し、低い定義から順に8個のuint32として返します。旧 `active_timer_mask` は互換性のため最初の32bitだけです。256bitをJSONの1つの数値へまとめてJavaScriptの整数精度を失うことはしません。256時計の同時登録、高い語の登録・期限・名前付き解除を検証します。

量補正グループも256へ拡張しました。GPUはグループ番号が実際の定義数より小さいことを検査します。コンパイラーが密な番号を発行する規約を使い、量補正の作業配列は256個を毎回初期化せず、実際の定義数だけ初期化します。同じ共通ソースの全容量初期化版と、32定義・64入力・3秒のGPU進行を各3回比較し、入力／全出力ハッシュが一致しました。中央値は70.75msから68.43msへ約3.3%短縮しました。この固定測定を実編成の性能へ一般化しません。

## 同名装備の成分

実データの装備補正は、同じ所有者・表示名で異なるstatを持ちます。これを1成分へまとめたり、後の成分を捨てたりせず、個別の定義として保持します。`element_bonus` は既存のstat ID17を使う正式な別名として受け付けます。

同じstatの量補正成分は前段のソース／グループ単位の規約を維持します。その他の同じstatの同名alias、一般スキルの同名キャリア、対象別の独立したスタック・期限は、未接続として拒否します。異なるstatを持つ装備成分を受け付けたことを、任意の複数キャリア対応の完了とは扱いません。

## 実際の所持・育成からの入力段階

`app/portable_roster_input.py` は通常の所持・育成・装備の準備を使い、5人の基礎値・静的武器・全ての実定義と、敵・操作／バースト方針を取得します。CPUの戦闘実行やtickは呼びません。`_portable_static_inputs` は内部の準備用フラグで、`full_battle_connected: false` を返します。未対応のキャラ定義や方針を黙って落として全戦闘の入力にする段階ではありません。

`verify-portable-real-equipment.py` は、この出力から**装備だけ**を明示的に選び、各45定義の初期化を203部隊でMetal実行します。通常の育成準備による非ゼロの攻撃22.22%・属性88.6%・最大弾数129.64%を含みます。GPU読み戻し後のCPU参照で5人全員の攻撃補正・弾倉・防御を照合し、除いたキャラ効果数と全準備定義のhashも保存します。CPUの途中状態はGPU入力にしません。

この検証は32を超える実データの接続を確認するものです。キャラ固有効果、戦闘の操作・バースト方針、全装備変種、敵世界を含む実編成の検証済み件数は0体のままです。通常画面のGPU受付も開いていません。
