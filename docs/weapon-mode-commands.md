# 武器モードと弾丸消費通知

`weapon_change` の `toggle: true` は、発動者の現在のモード名と定義の名前を比較します。同じなら終了し、異なるなら新しいモードへ切り替えます。終了はモードを先に消してから、その発動者へ既存の状態終了通知を送ります。子効果が同じ名前のモードへ入り直した場合、その新しい状態を親の終了処理で消しません。終了通知の実行器は期限切れ等の既存経路と共用します。トグルには空でないモード名と真偽値が必要です。

`instant / squad_ammo_consume_as` は、「実際の1発をN発として数える」ための追加通知です。追加分は `max(0, int(N)-1)` です。実弾の消費、射撃数、バーストゲージを追加しません。値はスキルレベルに対応した固定数量を使用し、GPUの通知プログラムの上限は4,096です。動的な倍率や他人への付け替えは推測せず拒否します。

弾丸消費通知は、既存のゲージ消費による通知と同じ実行器を使います。子効果がさらに通知を発生させても、親の残りの通知数は保持します。受け手となる定義が一つもない場合は、観測されない通知の列を省けます。受け手がある場合は順番に1発ずつ通知し、途中で変化した条件も再評価します。現在未発動の受け手も定義一覧には含まれるので、未発動・発動上限到達・戦闘不能だけを理由に省略しません。

検証では、別モードからの置換、トグル終了、期限切れ、終了通知からの再入、弾丸消費通知の親子処理を共通ケースとして確認します。実際のGPU射撃では、モード内の1発が40発分の通知を発生させ、実弾は1発だけ減り、通知後に増えた攻撃力が既に確定した親のダメージへ混ざらないことも確認します。

v69では、条件付きリロード完了効果が有効になるとリロードを始める判断もGPUへ接続しました。`weapon_mode_swap` は育成プロフィールの項目ではなく、全員に適用する真偽値の運用指定です。既定は無効です。通常画面の「詳細条件 → モード用リロード」から選択でき、保存と復元、結果キャッシュにも反映します。

条件付きの武器変更を既存のリロード完了イベント索引から探し、モード外・リロード外・装填後の待機外でのみ、現在の武器の装填時間を使ってリロードを開始します。入力は戦闘中のGPU状態から決定し、CPUが選んだ切替時刻をGPUへ渡しません。該当する条件付き効果がなければ、指定が有効でもリロードを追加しません。登録順と条件評価の順番を保ち、キャラ名で分岐しません。

通常武器の装填完了は射撃モデルの選択前に共通処理し、その場でモードに入った場合は新しい武器を選び直します。これにより、切替時に古い武器が1発射撃する問題を防ぎます。CPU側でも、装填からモードへ入り直す経路だけ射撃数・弾倉等の初期化が抜けていたため、通常のモード開始と同じ初期化へ統一しました。既存CPUの初期化漏れへGPUを合わせる変更ではありません。元の計算エンジンのファイルは書き換えず、対象の構文を検査する共通アダプターで接続します。

キャラ入力幅は168から169語へ増え、5人で40バイト増えます。効果命令は344語、状態領域は1部隊1,216,840バイトのままです。実行状態を新しい配列へ複製していません。

機能確認の後、毎フレームの全効果探索を既存のイベント19索引へ置き換えました。実スキルのモード射撃を含む通常APIの8候補で、キャッシュなしの単回比較は7,930.7435msから7,730.9025msでした。結果は同一ですが、中央値や全体性能の保証ではありません。全キャラ対応後に主要計算を改めて測り、全体の効率化を行います。

検証は、運用指定・条件・準備状態の共通4ケースと、実スキルを残す45秒の4ケースを使います。各フレームの弾数・装填期限・モード中の射撃段階と実際のモード射撃数を照合し、固定／蓄積ゲージ、切替なし、部位ありを含めます。CPUの観測履歴をGPUへ入力しません。標準条件で新たに受付するのはシンデレラ：クリスタルウェーブです。全キャラや実機仕様の検証完了を意味しません。

これら8ケースはnative/PTXの両方で通過しました。軽い共通検査83件、既存のモード射撃2ケースと発動順25ケースも通過しています。一括計算の確認は以前の8部隊を残し、切替の有効／無効の2部隊を同じ10部隊バッチへ加えました。部隊ごとに独立した結果と設定が保持され、CPUと一致しています。個別キャラごとに同じ検査群を複製していません。
