# 元編成の遮蔽物復活

`coordinate-original-cover`はビスケット全70、リリ全68定義を完全な元5人編成・武器・成長・auto操作のまま保持する6ケースです。各キャラで候補なし6秒、1人破壊46秒、3人破壊46秒を使います。実装済みの共通kind30 `cover_revive`をCPU／Slang共通の受付宣言へ接続します。CUDA／Metalは同じ静的入力・Slang実行器・比較器を使い、数値規約・wire・Runtime容量は変えません。

破壊は元武器の再装填中に宣言した敵攻撃が届くことで起こします。11.6秒にミランダ、複数候補では14.2秒のドレイク／メアリー、または11.6秒のリリと14.2秒のドレイクを追加します。HPに届く貫通攻撃や、注入した装填効果で代用しません。元の最初のburstでは候補がなく、43.466秒台の次のburstで復活します。CPUが計算した射撃／発火スケジュールをGPU入力へ渡しません。

CPU observerは元`_dispatch_instant`と実`revive_cover`の呼出し前後に保存済みcover HP／最大HPを読み、追加の対象解決やstat照会をしません。候補がない場合の無変更、実被弾数、1人または3人の破壊、実復活数、復活前0／復活後の実量、容量不変と対象外の保持を検査します。ビスケットは候補3人から2人、リリは3人から1人を実抽選します。復活量は実対象の保存最大HPに対する割合です。通常の全battle／packet／RNG／操作／healing比較と定義別dispatch数の比較も合成します。

リリの元効果順は保持します。「壊れた味方がいない場合」のbuff、壊れた味方への別の抽選buff、復活を並べ替えません。抽選したbuffと復活の対象をCPUで共有させることもありません。リリの複数候補には自身も含まれます。15秒ごとの元cover最大HP buff／通常cover回復も全定義・全期間に含めます。

初版のM5実行はビスケット3件が一致し、リリ3件は乱数比較で停止しました。短いリリの全624語は同じで、GPUだけ末尾に1語多く消費し、選択履歴はnative779／GPU780件でした。先頭128件は全一致し、余分な最終抽選は6.0秒の診断actor snapshotで、未解決の味方caster-ATK対象を固定していました。元CPUにはこのfinish時のget_buffs観測がありません。

修正は共通の既存`nativeNumericDiagnostic`規約を最終op40にも適用し、診断中の敵ATK読み取りでは結果に寄与しない味方late selectorを解決しません。実戦中の敵ATK読み取りと明示op39は元の順序を保持します。乱数の巻き戻しや比較除外を加えたものではありません。元CPUのlate random数値carrierが実際に未解決のままであることを確認し、GPUでも最終診断が対象を固定しないことを追加検査します。初版のclaim／rawと診断記録は保持します。

修正版v2はM5 Metalで全6ケース一致し、独立fresh監査104.724秒でも一致しました。初版で一致していたビスケット3出力の全21,238,272byteも保持しています。6入力／native指紋はすべて不変で、旧shield入口のCUDA/MSL原生成物は全byte保持しました。実GPUは計2回（初版の照合失敗1・修正版成功1）、同claim retry0です。修正版はCPU事前93.600秒、初回pipeline生成92.014秒、GPU計算6.565994秒でした。
