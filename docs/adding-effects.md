# キャラ・効果を追加する手順

## 既存の共通操作で表現できる場合

スキル定義と育成段階のマッピングを追加します。キャラ名による実行分岐や、同じ計算をする専用ハンドラーは追加しません。`app/effect_spec.py` は分類、`app/detail_gpu.py` は実行可能な形式の検査を担当します。分類済みでも未対応の形式は拒否します。

実スキルを削らない代表編成で発動を確認します。既存の数量・寿命・発動順の検査は再利用し、キャラごとのコピーを作りません。装備や配置で意味が変わる場合だけ、その違いを示すケースを加えます。

## 新しい共通操作が必要な場合

1. 数量の単位、発動者と対象、名前とインスタンスの識別、値の確定時点、丸めを定義します。発動・再付与・重複・期限切れ・解除・戦闘不能・復活の遷移も明記します。
2. `app/lifecycle_specs.py` に操作と依存順を登録し、CPUの `Handler` とGPUの処理を追加します。CPUは `app/effect_runtime.py` の共通アダプターを使い、新しい通知ラッパーを重ねません。未登録・重複・依存順の不備は起動時に拒否されます。
3. 戦闘中の状態は `RuntimeState` に置きます。存続中のインスタンスは `pool`、消滅後も参照する数量は `archive` に分けます。保持・消去の条件は操作側で指定し、別戦闘の状態を共有しません。
4. `scripts/generate-lifecycle.py` でCUDAの接続を生成します。手で生成部分を変更せず、`--check` と `scripts/audit-effect-runtime.py` でCPU/GPU両側の接続を確認します。CUDA変更時はnative/PTXの生成物も更新します。
5. 下記の観点で検証し、契約と根拠を `research` に保存します。
6. 新しい共通処理が動いた後、その処理の効率化を試します。同じ入力・結果を基準に、代表条件と負荷が出る条件を測ります。速度差が小さい、または確認できない場合も記録し、キャラ名による特例で速度を出そうとしません。

## 発動順の契約

通知は登録された依存順で同期実行します。子イベントを完了してから親の続きへ戻り、例外が起きても通知文脈を復元します。失効で状態を消してから終了通知を届ける操作では、終了時放出を済ませるまで必要な数量を保持します。

着弾や継続ヒットは、既存の実行器が持つ予約・継続の時点を保ちます。処理を共通化するために同一フレームへ前倒ししません。複数状態を更新してから通知する操作も、個別の更新直後に通知する操作と区別します。

## 状態の識別と初期化

同じ効果定義・発動者でも、対象集合が違えば複数の状態が同時に存在します。効果名は状態IDとして使いません。発動処理は今回作成・更新した状態を渡し、子イベント後の継続処理もその状態だけを参照します。CPUではオブジェクトの同一性、GPUではスロットと世代番号を照合します。親が解除された後に同じスロットへ別状態が入っても、親の残処理を引き継がせません。

`prepare_activation` は通常生成・更新・スタック初期化の共通入口です。子イベントが値を参照する前に必要な選択元や基準値を確定します。通常の発動後処理は `activate`、シールドなどの適用通知は `protection_activate` に接続します。単に実装を減らすために、これらの位相をまとめないでください。

最大HPの変更では、現在HPの増加とHP割合・条件の同期を分けます。スタック初期化時に割合の同期が必要な操作は `LifecycleSpec.initial_hp_stats` に宣言します。この宣言は現在HPを増やす指示ではありません。CPUの初期化文脈と、生成するGPUの同期判定で同じ宣言を使います。

基本ステータスコピーに加え、既存のシールド・デコイ・余剰回復保存・回復蓄積・ダメージ蓄積・最大HPスナップショットをこの識別契約へ移行しています。登録処理と実際の数量計算・対象選択を同じ状態に結び付け、過去の先頭検索・全件更新を置き換えています。v48ではnativeの新規27ケース、PTXの17ケース、全体回帰216件、通常APIが通過しました。軽量110件は全体回帰の部分集合です。再現前の結果は `research/ports/v47-before-carrier-migration/research/legacy-carrier-audit.json`、修正後は `research/legacy-carrier-audit.json`、検証記録は `research/carrier-checkpoint.json` を参照してください。

GPUで発動後処理を持つ新しい操作は `LifecycleSpec.current_instance=True` を宣言します。生成器がスロットと世代を照合する接続を作り、接続監査が宣言漏れを拒否します。基準値を子イベント前に確定する必要がある場合だけ `gpu_prepare` と `prepare_activation` を追加し、効果ごとに独自の通知ラッパーを作りません。一般のダメージ・射撃処理など、カタログ外の実行器をすべて置換したわけではありません。

## 重複を増やさない検証

| 検査 | 確認すること |
| --- | --- |
| 独立した期待値 | 最小の手計算で数量・丸め・上限・消費を確認 |
| 状態遷移と順序 | 再付与、同時失効、入れ子、解除と放出、例外後の復元 |
| 相互作用 | 関係する既存操作との組み合わせ。全キャラの直積は作らない |
| 代表部隊 | 実定義を残して部隊合計・各人・バースト・状態推移を比較 |
| コンパイラー境界 | 曖昧な名前や未対応フィールドを黙って受け付けない |

`scripts/resource_frame_capture.py` でCPU状態を読み取り専用で観測し、GPUの毎フレームと終了時の状態を比較できます。CPUの状態や発動時刻をGPUへ入力しません。

`verification_session` は同じ検証器・入力・追加条件・バックエンドの成功結果だけを同一プロセス内で再利用します。関係するソース変更や参照処理の差し替えで無効化します。失敗は再利用せず、別実行の古い結果もキャッシュしません。

軽い確認は `scripts/verify-normal-detail.py --scope fast`、回復系は `--scope recovery`、共通実行器など影響範囲が広い変更は `--scope full` を使います。軽い確認は全体検査の部分集合なので件数を足しません。局所的な効果追加は当該の数量・相互作用・代表編成と関連回帰を選び、選択理由を記録します。

開発中は、まずCPUの独立した期待値と使用中GPU向けnative版で共通処理を確認し、次に同じケースで効率化を比較します。最終版でnative/PTXの生成物と照合をそろえます。共通処理の仮版と効率化後の版の両方でPTXの初回JITを繰り返す運用は避けます。バックエンド固有の挙動が疑われる場合は、必要な段階で両方を確認します。最終版の検証範囲は減らしません。

両方の生成物を記録する通常APIの最終確認は、native/PTXのファイルをそろえてから実行します。未使用側の生成物を後から更新したことで検証記録のハッシュだけが古くなり、再実行が必要になる順序を避けます。

比較元の入力・生成物・結果は保存し、結果キャッシュによる短縮を速度改善に含めません。GPUカーネル、準備・転送、復元、モジュール初期化を区別します。初回コンパイルやJITの待ち時間が支配的なら、数量検査を削る前に生成物を作り直す回数を減らします。全キャラの直積や同じ比較器のコピーを追加せず、共通の順序・境界・相互作用の検査を使います。

## 全キャラ対応後の全体最適化

全キャラ・残りの効果への対応が終わった後に、全体の効率化をもう一度見直します。各共通操作の速度比較だけで、この段階を完了したとは扱いません。

候補生成から結果表示までを再計測し、共通命令の再利用、GPUへ渡す単位と一括サイズ、状態・定義のメモリー配置、カーネル内の走査と実行、転送、結果復元を確認します。必要なら実行形状も検討しますが、状態・乱数の独立性と発動順を検査してから採用します。単体・複数部隊・重い効果の組み合わせを含む同じ入力で前後を比べ、実際の待ち時間とGPU時間を分けて記録します。上限条件だけの高速化を通常の編成へ一般化しません。

## CPUと実機の扱い

CPU一致は回帰の手掛かりです。実機の根拠と矛盾するなら、独立した期待値を用意し、CPU参照とGPUを修正して意図した差を記録します。根拠が足りない相互作用は仮定として明示します。コンパイル受付数、CPU一致数、実機検証済みの範囲を混同しません。

## 現在の移行範囲

デコイ、シールド、余剰回復保存、回復分配、回復蓄積、ダメージ蓄積、最大HPスナップショットの状態フックを共通カタログへ接続しています。汎用の戦闘実行器すべてを新しく置き換えたわけではありません。既存キャラの移行検証は `research/runtime-lifecycle-checkpoint.json`、その後の拡張は `research/damage-accum-checkpoint.json` と `research/max-hp-snapshot-checkpoint.json` を参照してください。

最大HPに関する効果でも、発動者の最終最大HPを使う付与と、別の味方の基本HPをコピーする効果では、対象の選び方と更新時の挙動が異なります。コピー系の資料比較は `research/copy-stat-evidence.json` に記録しています。既存CPUが未実装の効果や、注記と観測資料が食い違う効果は、数量がゼロのCPU一致で実装済みにしません。

## 候補の一括実行と検証の再利用

`detail_gpu.evaluate_full` と `evaluate_full_many` は同じ入力生成器と結果復元器を使用します。一括化のための別の計算式やキャラ別処理は追加しません。命令列が完全に等しい候補だけをまとめ、各部隊の効果・敵・基礎値・乱数・状態領域は別々に渡します。Pythonワーカーは単体・一括とも `evaluate_details` を通し、通常APIのキャッシュと結果順は `evaluation-queue.mjs` が管理します。

GPU命令と数式を変更しないホスト側の一括化では、全キャラの数式テストを追加・再実行せず、グループ分け、結果復元、失敗時の後始末、CPUへの切り替え、キャッシュ、停止・再開を検査します。今回は実8部隊のCPU照合、凍結済みv48単体実行との異なる時間・乱数を含む比較、通常APIの所持装備・育成変更と性能測定を選びました。v48の全体回帰216件は変更前の基準であり、変更後に再実行した件数として数えません。

## 名前付き攻撃対象の参照

`named_target_specs.resolve_named_attack` は、同じ発動者の効果名から参照先を一意に決定します。キャラ名で分岐せず、直接攻撃の固定ヒット数と追加ダメージ自身の係数用スタック参照を別の数量として扱います。現在の敵モデルは照準対象が1体なので、対象の継承はその敵に対応します。複数敵の個体識別を実装した意味にはなりません。

B3のバースト追加ダメージは既存の保留実行に接続します。参照した攻撃回数は入力命令の52番へ格納し、係数用の状態はフルバースト開始時に参照します。後続の同時バーストバフを除く既存の処理順は維持します。通常の対象指定は従来どおり1回です。欠落・重複参照、動的ヒット数、間接参照、リスト内の参照、DoTの段階的な重ね掛けは、この直接追加ダメージの仕様では受け付けません。DoTを追加する際は、予約・上書き・解除・期限の共通状態処理を実装してから対応範囲を広げます。

仕様は `research/named-target-contract.json`、実行中の検証状況は `research/named-target-progress.json` に記録します。コンパイル受付の増加だけで戦闘計算の確認済みとは扱いません。

名前付き参照のv49検証はnative・PTX各8ケース、通常API、関連する既存20ケース、仕様・境界8検査で通過しています。4体の実編成は条件付きの追加効果が実際に発動したことも観測します。生成命令が同一だった既存902条件と、新規受付21条件を区別し、軽い検査の先行実行分を重複加算しません。確定記録は `research/named-target-checkpoint.json` に保存します。

## 大きなCUDA生成物の検証順

この規模のnative生成と、PTXの初回読み込みは直列に実行します。v50の追加時は並行実行中にシステムの仮想メモリー空きが約2.6GiBまで減り、自分のPTX検証だけを停止すると約21GiBへ回復しました。記録は `research/damage-basis-resource-control.json` です。ビルド・JITが重い間は、CPUだけの入力検査や仕様調査を進めます。数値検証や速度測定も、その前提を記録して実行します。

出力がまだない場合は、起動時に返った同じハンドルを確認します。観測待ちの時間切れだけで再起動しません。メモリー圧迫のような実測した理由で停止した場合は、対象プロセスの同一性、停止理由、終了結果と、未検証であることを保存してから再実行します。ソースと使用する生成物は、検証を開始する前に確定させます。

詳細CUDAのビルド入口は `detail_build_contract.checked_detail_abi` で、CUDAのカーネル名とPythonのABI宣言が一意に一致することを、コンパイル前に確認します。生成物のABI名を各ビルドスクリプトへ重複記入しません。不一致・欠落・重複は軽い検査で拒否し、長い生成後の読み込み失敗を避けます。

## 最大HPを基準にした攻撃と条件付きの装弾数

`damage_basis_specs.damage_basis` はスキル単位の攻撃基準を検査します。加算型は現在の最終最大HP×割合を固定攻撃力の項へ加え、通常の攻撃力％・固定値を残します。置換型は同じHP基準値で攻撃力を置き換え、通常の攻撃力％・固定値を適用しません。防御力・ダメージ倍率・クリティカルの層は共通です。ヒット数や係数用スタックとは別の数量で、現在HPが減ったときも最大HPを使います。入力命令53・54が方式と割合を保持し、状態領域は増やしません。

装弾数減少の排他指定は、負の付与グループに指定がある場合だけ有効です。指定のない減少も含め、丸め前のグループ合計が最も小さい1組を採用します。同率は先の1組、正の増加はすべて残し、最後に最小装弾数を適用します。期限切れや正の排他指定では減少を抑制しません。stat参照と実効装弾数は同じ選択関数を使い、この機能を持たない編成では従来の経路を使います。

`self_undying` は付与元や名前ではなく、本人に存続中の不屈状態があるかを判定します。`no_broken_cover_ally` は本人を含む生存メンバー全員の遮蔽物を確認します。戦闘不能者は対象外です。現在は明示的な発動イベントで検査し、未対応のパッシブ形式を拒否します。条件通過後の有限時間バフは、その付与寿命に従います。

数量・丸め・同率・期限・遅延対象は共通の期待値表で検証します。実編成では元のスキルを残し、遮蔽破壊→復活と反対条件の両分岐、不屈中の付与などが実際に発動したことを必須にします。敵の攻撃がある場合は被弾・HP・遮蔽・乱数を比較し、攻撃がない場合は既存の部隊全体比較器を再利用します。存在しない敵攻撃の観測項目に合わせて検査を弱めません。仕様は `research/damage-basis-contract.json` です。

## 関数展開を抑える効率化

v50では共通の条件判定・stat参照・排他装弾数選択を明示的に非インライン化しました。数式・状態レイアウト・ABIを変えないことを正規化したソースの完全一致で確認し、数値検証は別に行います。PTXは21,507,327から10,862,177バイトへ減少しました。以前のnativeビルドは30分以上経って未完了、変更後は304秒で完了しています。前者は停止したため、完了時間の倍率は算出しません。

変更後のnativeコンパイラーは約10.0GBのピークコミットでした。以前の処理は途中の観測で約32.8GBでしたが、これはピーク値同士の比較ではありません。`research/profile-detail-build.py` は自分が起動したコンパイラーだけを観測し、実時間とOSのピーク値を保存します。同じ8候補の通常API計算は4.66秒、直前の一括版は4.81秒で、単発測定ではほぼ維持したと扱います。コードサイズの減少だけで戦闘計算が高速化したとは判断しません。

## 使用時に確定し、フルバースト開始後に着弾する攻撃

`attack_timing_specs.full_burst_landing` は明示された予約指示を検査します。発動条件と発動回数制限は使用時に一度だけ確認し、stat末尾の固定回数・名前付き数量を保持します。着弾時は条件や使用回数を再判定せず、通常の共通ダメージ処理へ再開します。係数とバフは着弾時に参照します。欠落した回数参照は0回です。周期攻撃・予約追加ダメージとの曖昧な二重指定・別形式の回数参照は現在拒否します。B1・B2ではこの指示で着弾を遅らせません。

命令51は従来の追加ダメージ予約が1、新しい着弾予約が2です。命令52は固定回数、または4096＋名前IDです。固定値の負数を名前IDと混同しません。既存の予約配列を共有し、状態領域を追加しません。着弾再開でも、親のダメージ・クリティカル率を確定してから命中ごとの子イベントを実行します。親だけに適用する後続バフの除外を、子のダメージ参照へ漏らしません。

フルバースト開始時の通常効果→従来の追加ダメージ計算→新しい予約攻撃計算の順を保ち、その着弾による回復・ダメージ蓄積・部位処理を同じフレームの通常射撃より先に届けます。以前から次フレーム待ちのダメージと、着弾通知が新しく生成したダメージは元の待ち列へ残します。検査は手計算のダメージ・回復量、条件の消失、回数参照の変更、子イベント、B2、0回、欠落参照と、既存の予約追加ダメージを再利用します。全体検査では既存の予約追加ダメージ検査を新モジュールへ複製しません。

この操作が実装できたことと、キャラの実際の着弾フレームを実機で確認したことは別です。エレグ：ブーム・アンド・ショックの資料には時期による記述差があり、元データにはゲージ最低残量が未実装という注記もあります。不屈等とは別の憑依マーカーやゲージ残量を未対応のまま無視して、そのキャラ全体を対応済みにしません。根拠・未解決事項・検証状態は `research/deferred-attack-contract.json` と `research/deferred-attack-progress.json` に記録します。

`DamageQueryScope` は、親攻撃の発動者と除外する付与名を保持する変更不能の参照範囲です。通常バフの集計だけでなく、名前付きのスキル倍率と攻撃用の最終最大HPにも同じ範囲を渡します。他の発動者による同名付与は除きません。HP管理・回復の上限・コピーの基準値など、通常の最大HP参照はこの攻撃用の除外を受けません。状態リスト自体の削除・差し替えは行いません。

## ゲージ消費後の最低残量

`resource_specs.minimum_remaining` は `gauge_consume` と `gauge_consume_as_ammo` の消費操作だけに適用します。充填時の上限や常時の下限ではありません。消費後は `max(最低残量, 消費前−要求量)`、全消費の指定−1では最低残量を残します。元の残量が下限より少なければ下限へ戻りますが、充填・捕獲の通知は発生させません。

実消費量は要求量と「元の残量から最低残量を引いた利用可能量」から求めます。丸め後の残量との差から逆算しません。大きな値から小さな要求量を引くと残量が同じ浮動小数点値へ丸まっても、要求した消費に対応するイベント数を失わないためです。弾薬として数える操作だけが実消費量の整数部分を通知します。入れ子の子イベントで再充填されても、親が確定した消費量と通知回数は変えません。

CPUでは既存の即時実行器へ数量処理を合成し、生成・スタック初期化の準備と終了後の状態回収を保ちます。周期操作は登録時に消費せず、元の刻みで実行します。GPUは同じ数量仕様を命令294番へ追加し、命令幅を295としました。状態領域に新しいゲージ配列は追加しません。

元データの不足を補正する場合は `data/engine-effect-overrides.json` に、キャラ、効果を一意に決める旧フィールド、新しいフィールド、根拠を記録します。`effect_overrides` は起動時に一度だけデータを複製して補正し、欠落・重複・重なる補正を拒否します。固定した取得元ファイルは変更せず、計算処理へキャラ名の分岐を追加しません。補正データは通常サーバーの実装ハッシュにも含めます。

エレグ：ブーム・アンド・ショックの6消費側には最低残量1をデータで補いました。これは消費部分の補正であり、弾薬消費による捕獲の近似を解消した意味ではありません。対象別の命中・死亡時の捕獲・上限へ達する前後の順序は別に対応します。既存の本体／部位命中カウンターは非コア命中の流れなので、その名前を変えるだけでは実装できません。調査は `research/target-counter-dependency-audit.json`、数量仕様は `research/resource-limits-contract.json` にあります。

v52の確定記録は `research/resource-limits-checkpoint.json` です。数量14・部隊2・既存ゲージ9の計25ケースを両バックエンドで確認し、既存の予約攻撃／参照範囲14ケースと一括8部隊を命令幅変更の関連回帰として選びました。通知回数を示す観測の強化前後の実行は同じケースの再確認なので、カバレッジ件数を足しません。全体216件を再実行したという意味ではありません。

## 段階的な継続攻撃

`staged_dot_specs` は段階の間隔、係数に使うスタック、段階終了後の通常周期までの待ち時間を共通の仕様として検査します。`staged_dot_runtime` は付与時に回数を確定し、保持するスタックと、その攻撃だけの係数参照を分けます。回数の参照が存在しない場合の既定値1と、存在して0の場合の不発動を区別します。同名の親攻撃が曖昧な場合や上限を超える指定は拒否します。

再付与時は古い世代の予約を無効にします。子イベントの再付与・解除・例外の後で、親が古いスタックを復元しません。通常の周期攻撃は最後の段階から指定された待ち時間の後に始まります。CPUとGPUで同じ発動時刻・登録順の優先順位を使います。GPUは定義ごとに待ち列の位置を保持し、更新時に古い予約を取り除いてから新しい予約を入れます。CPUの不要予約をまとめる場合は、実行中の待ち列の参照を保持します。

検査は固定係数・累積係数・上限・再付与・解除・入れ子の共通期待値と、既存の部隊比較器を再利用します。効率化の比較元は `research/staged-dot-native-stage.json` に保存しています。64個同時の待ち列による負荷試験と通常APIの8候補を別々に測定し、同じ入力と結果を確認します。

親攻撃の連続ヒットを一括計算する既存の近似が残るため、計算結果には着弾時刻が実機未検証である旨を表示します。CPU一致や待ち列の高速化だけで、この近似を実機どおりと扱いません。

## 値を使う時点の装弾数と、通知元の攻撃量

`quantity_specs.validate_quantity` は数量の参照元を検査します。`max_ammo_count` は受領者の最終最大装弾数を数値バフへ掛けます。付与時に固定せず、装備、バフの丸め、武器変更を含む通常の装弾数計算を使います。同じ受領者の装弾数を問い合わせている間は、この倍率を再帰的に参照しません。値と発動回数、発動者と受領者を混同しません。

`dealt_fixed_damage` は通知元の攻撃が保持するダメージ量の割合を、正の値だけ一度切り捨てて本体へ届けます。防御、攻撃力、クリティカル、コア等を再適用しません。この固定ダメージ自身による名前付き命中通知やバーストゲージ加算は行わず、既存の型付きダメージ通知へ接続します。親の攻撃量がない通知では0です。子の別通知へ親の攻撃量を漏らさず、子の処理後には親の参照範囲が続きます。

新しい数量を追加する場合も、参照元、参照時点、受領者、再入時の扱いを先に定めます。共通の数量検査と部隊比較器を使い、キャラ名で計算式を切り替えません。装弾数の効果切れ・武器変更、子通知、次弾への適用は共通ケースで確認します。仮版の確認は `verify-common-runtime-unit.py --native-stage`、生成物がそろった最終版は同じ入口で全検査を実行します。

数量の仕様と根拠の限界は `research/quantity-sources-contract.json` に記録します。公式スキル表記の確認と、同一フレーム内の適用順や部位を含む攻撃量の実機検証を分けます。

効率化の試行では、通常の値取得をインライン展開し、装弾数の再帰問い合わせを別関数に分ける案を比較しました。新しい数量参照を使う8候補は約3.6％遅く、既存の8候補は約1.3％速い単発結果で、安定した改善を確認できませんでした。この案は採用せず、検証済みの元の版へ戻しています。候補の生成物と結果は `research/quantity-lookup-experiment.json` に保存し、改善しなかった試行を速度向上として数えません。

## 同時命中する対象の収集（移行中）

`attack_group_specs` と `attack_group_runtime` は、攻撃の開始から確定までの対象を保持する共通基盤です。明示された攻撃グループについて、CPUとGPUの収集と条件通知を確認しています。自律戦闘の実際の射撃・敵世界から境界を渡す処理と、命中先それぞれへ子効果を適用する処理は未接続です。`multi_hit:N` の通常GPU受付は引き続き拒否し、この基盤を追加しただけでキャラの受付数を増やしません。

現在の命中先は対象カウンターの子通知より先に収集し、攻撃グループを確定・切り離してから条件を満たす通知を登録順に送ります。子が同じ公開攻撃IDを再利用しても別世代として扱い、古い親の終了処理で消しません。リセットや生成側の例外は保留グループを破棄します。既存の攻撃ID0の通知は、生成側が正しい境界を渡すまで収集しません。

効果定義は戦闘中不変として、発動者ごとの通知計画を再利用します。定義の再登録・置換やリセットで参照表を更新します。CPU基盤の機能確認後、200定義・5,000攻撃の共通処理を3回ずつ測り、中央値約159msから27msへ短縮しました。GPU・実戦全体の速度改善を示す測定ではありません。記録は `research/attack-group-contract.json` と `research/attack-group-cpu-checkpoint.json`、最適化前の基準は `research/attack-group-cpu-stage.json` にあります。
