# 共通の資源数量と境界通知

資源を `(所有者, gauge_id)` で識別し、数量・存在・宣言済み基本上限を共通Slangが保持します。CPU計算の途中数量や通知順は入力しません。`gauge_charge`、`gauge_consume`、`gauge_consume_as_ammo`、`gauge_max_add`、状態マーカー `gauge_charge_enabled` と `every_stack`、`gauge_above/below/eq/mod` を接続します。CUDA／Metalは同じ定義・梱包・実行器・期待値・独立CPU参照を使います。

## 数値と状態

- 数量は整数演算によるソフトウェアbinary64。Metalのnative doubleやfloat32への縮小は使いません。
- 消費後数量と実消費量は別に計算します。`1e16 - 1 == 1e16` の場合も実消費1を保持します。最低残量・全量消費 `-1`・負の要求・負の現在量を共通の資源規約で扱います。
- 弾薬消費通知は各操作の実消費を整数へ切り捨てて発生します。小数の余りを次回へ繰り越さず、物理弾薬と混同しません。
- 上限宣言はその操作に数値がある場合に更新します。消費時には現在量を上限へ切り詰めず、次のチャージ時に適用します。上限加算は有効リスト上の同じ所有者・キーのraw literalを加算し、stack数や受領者条件を掛けません。大きな加算値の相殺には既存の補正加算を共用します。整数literalをbinary64へ正確に表せない場合は受付を拒否します。
- `gauge_mod` はbinary64の符号・指数・仮数から整数部の非負剰余を求めます。int64を超える値・負数・小数も狭い整数へ変換しません。法は正のint32です。
- `above` は以上、`below` は未満です。両者は照会時に再評価し、`eq/mod` は発動時の条件を保持します。
- ダウン時にその所有者の数量だけを0へ戻し、キーの存在と宣言済み基本上限を保持します。マーカーは名前付き状態であり、無関係なチャージを遮断しません。

## 通知順

チャージ後の数量を先に確定し、元の変更前後から各 `every_stack` の境界の昇順和集合を作ります。子の消費・チャージが親の境界範囲を変更しないよう、明示フレームへスナップショットを保持します。重複した通知記述の配信回数と、境界イベントそのものの重複排除を区別します。所有者・資源別の記述索引をGPU上で構築し、全定義走査版も同じSlang内のコンパイル切替で保持します。

境界列挙はint64範囲とbinary64で正確に表せる整数境界に制限し、範囲外はstatus 2で失敗させます。トレース上限超過も失敗させます。この制限は剰余計算の有限binary64対応範囲とは別です。通知の歩幅と各操作の弾薬通知数は正のint32範囲（通知数0は可）とし、総通知数もint32上限で停止します。

## 配置と確認範囲

ABI `0x50455651`、入力57,344・出力65,536 words。資源キー最大256、所有者5、定義256、通知記述8、数量照会64、詳細通知トレース128です。旧ABIから入力4,096・出力12,288 words増えます。GPU実割当や全編成の性能をこの配置だけから推定しません。

`tests/fixtures/portable-resources.json` の32ケースは元のBuffManagerと共有資源パッチを使って独立参照し、GPU入力には参照結果を渡しません。上限相殺の整数・浮動小数点2ケースを含みます。初回Metalパイプラインは300秒のコンパイル上限に達しました。`research/portable-resources-initial-compile.json` に失敗を保存しています。その後ドライバーから `Compute function exceeds available stack space` を取得したため、資源状態・通知索引を各プログラム専用の出力領域へ移しました。資源定義の数値も入力から必要時に読み、全定義の私有コピーへの追加を避けています。失敗記録はsecond/third-compileにも保持します。実機検証の最終結果はチェックポイントと検証記録に追記します。

資源によるダメージ倍率、資源参照の命中回数、世界スケジュール、残る効果・装備・全変種の対応は別途必要です。資源の部品検査だけで全キャラ対応とせず、通常画面はCPUを維持します。
