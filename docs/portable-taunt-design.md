# 挑発と敵の味方対象選択（調査中・GPU受付無効）

`taunt` は203体の現行カタログで未受付の25効果に現れます。HP由来攻撃力の固定ソース検証中に、次の敵対象処理として元CPUを調査しました。現在の共通実行器には入れていません。

`research/characterize-taunt-native.py` は元BuffManagerで180条件と120通りの複数所有者の発動順を確認します。全5所有者、自己／全味方／ボス、負・ゼロ・正の量、無限／有限期間、条件失効と期限を含みます。数量の符号やゼロは挑発者の有無に影響しません。複数挑発者の結果は発動順ではなく部隊順です。

元の `taunters(t)` は各効果から最大1人を取り出します。味方対象では保存された対象順の最初の有効受領者、敵対象では付与者を使い、重複を除いて部隊順に並べます。全味方対象だから全員を挑発者にする実装にはできません。敵対象の枝では `_live` を通らないため、味方対象と実行時条件の再検査規則が異なります。どちらも期限を検査します。元CPUとの違いを許容する例外を増やす代わりに、枝ごとの入力・期待値で明示します。

元timelineの `_attack_targets` は、全体攻撃では生存者全員を選び、挑発・隠密を参照しません。固定座席では挑発者へ先に座席を割り当て、残りを指定順で補います。ランダム／攻撃力順位では挑発者以外の生存者から隠密を除きますが、全員が隠密ならその残り集合を使います。`ignore_taunt` と不足人数の処理も別に必要です。これらは現段階ではソース読解であり、今回のBuffManager調査が敵攻撃の実行を認証するものではありません。

接続前に残る観測は、実際のsimulate内の敵攻撃、死亡・復活、無限順位対象の未解決／解決、対象の死亡・退出、複数効果の重複と解除、隠密との組合せです。ランダム選択は共有RNGの状態・消費回数まで設計します。CPUで選んだ対象マスクをGPUへ送る実装ではなく、ボス攻撃の規則と時刻を入力にしてGPU内で対象を決定する必要があります。

現在の入力コマンド25は明示的な味方対象マスクを使う受撃成分です。そこへCPUの挑発結果を入れて対応済みと数えません。挑発・隠密の状態と敵攻撃の対象決定を共通の実行器へ接続し、選択順・受撃・HP・保護層・後続通知まで元の実行結果を検査することが次の段階です。全キャラ認証は未完了です。

追加の `research/characterize-taunt-boss-native.py` は、元simulate・元の敵対象選択・元の受撃処理を使って105条件を確認しました。全5所有者×自己／全味方／敵への挑発、全体／固定2番席／攻撃力上位1人／ランダム1人、全体以外の `ignore_taunt` を含みます。挑発有効なら挑発者1人、全体なら部隊全員、挑発無視の固定席なら2番席へ入ることを実際の `squad_hits` で検査しています。挑発無視の順位／ランダムについては人数だけの検査であり、順位や共有RNGの認証とは数えません。登録する効果と武器メタデータだけを入力として置き換え、対象選択・射撃・受撃関数は置き換えていません。

敵対象の追加研究では、初版の人数だけの検査を強化しました。挑発無視の攻撃力順位は元の初期base_statsから選んだ1人を照合し、期待値モードの敵用固定シード0では最初のランダム対象が4番席になることも固定値で検査します。利用者指定のseed19と敵用の実効seed0を記録上で区別しました。全105条件の対象を検査しますが、共有RNGの実装・複数回の消費列はまだ未検証です。初版は `portable-taunt-boss-first-native-study.json` に保持しています。

隠密との組合せを加え、実simulateの対象検査は420条件へ拡張しました。隠密なし・挑発者だけ隠密・それ以外が隠密・全員隠密を調べ、挑発が隠密より先に座席を取り、全員隠密では候補集合を戻すことを確認しています。全体／固定席は隠密を参照しません。この調査もGPU受付や共有RNGの実装を意味しません。
