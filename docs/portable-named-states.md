# 名前付き状態条件・適用通知の共通実行

`self_state:`／`not_self_state:`、`event:`／`event:state_end:` の名前部分を完全な文字列として扱います。コロン・空白・改行・Unicodeを分割、除去、正規化しません。状態の作成者と受領者を区別し、条件は効果の作成者がその状態を受領しているかを調べます。武器モード名も同じ名前解決を使います。有限時間バフの条件は発動時だけのゲート、永続バフの状態条件はクエリ時にも再判定する既存CPU仕様を保持します。空の `self_state:` も既存の「モードなし」と一致する特殊規則を保持します。

HPしきい値・状態終了などの構造を持つ通知は、名前付き通知の一般形へ誤って流しません。空の状態終了名、不正なHPしきい値、未対応の `accum_full:`／`target_counter_complete:` 通知と既知の未対応イベントは引き続き拒否します。スタック／ゲージ条件などの名前付き数値構文は、CPU自体がコロン名を処理できないため今回の受付拡張に含めません。

## 適用通知と実行順

受付を拡張した実GPUテストで、`event:stat_applied:dot_dmg_pct` と `event:stat_applied:split_dmg_pct` がGPUから出ていない差が見つかりました。最初の41ケース中2失敗を `research/portable-named-states-initial-failure.json` に保存しています。期待値を変えず、共通Slangの既存バフ適用フレームと21対象の通知配送器へ接続しました。

名前付き通知・スタック通知の子処理を完了した後、初めに選んだ対象順で適用通知を送ります。重複は重複したままです。途中の名前付き通知が親バフを削除しても、CPUのローカル対象リストに相当する捕捉済みリストを使い続けます。未解決の遅延対象には通知を送りません。名前のないバフ、max_stack=1の更新、11／21対象の後半も検査します。通知の子処理を終えてから既存の参照捕捉・免疫・保護層・HP後処理へ戻ります。

ABIは `0x50455669`。既存health-definitionのbuffEventワードの下位2bitは名前付き通知／対象範囲を維持し、上位bitに任意の適用通知名ID＋1を格納します。0は通知なしです。タグ範囲、対象stat、効果kindはGPU側でも検査します。入出力は86016／159744 words、Runtime・Definition・Frameのフィールドや私有配列は増やしていません。生成CUDA／MSLを別々に修正する経路はありません。
