# ペルソナ状態と本来のバースト3対象

canonicalのpersona_stateはkind4／stat0／quantity flag1の存在マーカーです。数値が0・負でも状態として存在し、別名のペルソナも同じstatで判定します。CUDA／Metal共通の状態・carrier・期限・解除・stack・発数寿命を使い、新しいRuntime配列は追加していません。

`allies_burst3_persona_excl_self`はcanonical selector18です。不変の本来のバースト段階mask、自己除外、生存者、既に解決済みのマーカー所属からGPU内で対象を決めます。現在段階へのoverrideや、直近のburst castとは独立です。順序は部隊順で、通常の複合selectorにも同じleafを使います。

参照はpinned BuffManager._has_persona_stateと_resolve_targetです。存在判定は値・stack・runtime条件を再評価せず、未解決のlazy markerも強制解決しません。期限処理前の_active相当の生carrierを見ます。既存numeric queryがlazy所属を解決する通常の順序は維持します。

## 受付と検証

Pythonはprivate combat worldの味方marker／selectorだけを受け付けます。GPUはkind・stat・flag・finite value・enemy／health metadataを検査し、selectorのcount／mask／余剰語も検査します。既存gear flag32との共存は認めますが、stun／charge等の混在flagをpersonaとして受け付けません。

最初の独立33入力（native21＋拒否12）はMetal／native全一致しました。CPU参照では「対象の味方のdamageが実際に増える」ことを別に確認し、単なる空対象の一致で済ませていません。数値0／1／負、異なる名前、自己除外、B3制約、現在段階override、付与前／named子／失効子、finite条件と常時runtime条件の違い、stack、解除、戦闘不能、複合対象、equipment源を含みます。

さらに0stackでも存在するケースと発数寿命を追加しました。最初の集約522ではクイーン／ユキコの4入力が受付拒否され、他518入力は成功しました。既存の診断入口でクイーン3秒だけを調べ、共有評価器が既に処理できるTARGET_CODE（44）がactor-field追加条件の受付から漏れていると特定しました。

target_codeが一致／不一致の正例と不正参照を加え、開発41入力（native25＋拒否16）にしました。静的counter viewの再コンパイルでも同じenemy-code名前表を再構築し、完全な名前表一致の検査を維持します。診断文の比較やnamespaceの部分一致へ緩めていません。

クイーン（マコト）／ユキコ／アイギスの全定義実編成を各3秒／30秒、3人同時の実編成も3秒／30秒で追加しました。修正版の集約530（native412＋拒否118）はApple M5 Metalで全件一致し、明示seal済みです。旧481・独立33・原522の成功518は全input／raw／native同一です。原失敗と診断captureは保持しています。

実編成の物理履歴は既存の2048件上限と省略件数を検査します。ユキコ30秒は32件、3人同時30秒は2123件の履歴省略を明示記録しています。全damage／HP等の戦闘状態と記録された物理履歴・省略件数は一致していますが、省略された各packetのsnapshot一致とは主張しません。全キャラ認定や通常UIのGPU接続とも区別します。

静的packingは199/266、基本キャラ140/203、分類106です。packingはGPU受付・実戦一致とは別の段階です。Windowsのcold compilerは再実行していません。
