# フルバースト開始後の共有GPU着弾

`land_in_full_burst` をCUDA/Metal共通Slangのprivate実行器へ接続した。正本13契約をMetalで比較し、元イレグ：ブーム＆ショックの全76定義も3秒/30秒で一致した。通常UIはCPUのままで、全キャラ・全効果の認定ではない。

入力は既存damagePendingを別mode2として使い、非weapon MODE17..19へ専用タグFBL1と予約0を格納する。MODE20..23のHP basis、24..27の名前付き敵、28..31のentry情報とは重ならない。cast時の条件・budgetを再評価せず、回数を既存pending配列へ保持する。静的な負の回数はsigned32のbitを保存し、実行回数へ変換するときに0へclampする。参照名は既存のstate/resource表で解決し、CPUで値を読んで入力しない。

係数・除外scopeをlanding時に読み、既存のFrame10とtyped receipt経路を使う。内部mode34は既存フレーム実行器へ直接入るため、条件・budgetを二重に消費しない。cast/landing両方に参照読取を残し、landingの実行回数はcast時の固定値に戻す。生成MSLでも二つの呼び出しを確認した。GPU上の各参照値1/2を専用traceで直接観測したわけではなく、正本の読取契約・生成コードと固定1回のGPU出力を別の証拠として扱う。

新しい親と名前付きヒットの子が生成したreceiptの範囲だけを、フルバースト開始フレームで着弾させる。前から通常キューで待っていたreceiptや、物理着弾中に追加されたtailを巻き込まない。前回の設計で曖昧だった子の時刻も固定し、親3150と子1260/1323/1386は全て同じ35/60秒に作成・着弾する。従来B3 bonusと新modeは計算段階を分け、旧pending counterへ新modeの件数を加算しない。

固定package `ecef6bcd667379fc7de33503d51aecc6e7d075c57ecb87e686bade2aa39ec3fc` のMetal258(native186/拒否72)と独立sealが成功した。内訳は旧230、前回の元アスカ2、新規合成13と不正13である。新規には1/3/13hit、0/負/未所持参照、cast1→landing2の読取と固定1、flag false、stage2即時、従来bonus、前後の倍率、親子がある。mode/tag/予約/人数/参照/stage/cast/combatの不正を拒否した。

旧230と元アスカ2の全input/native/output指紋を保持し、raw729,808,896バイトも一致した。Runtime全fields/offsetとstride138952は同一で、入出力容量も増やしていない。binary64、整数/pow primitive、normalizer、正本、既存CUDA計算器は変更していない。

初回packageの258は倍率が後の1件だけが不一致だった。入力の除外maskは正しかったが、生成MSLで係数計算前の一時damageExclusion代入が消えていた。倍率の除外を親rowの不変maskから直接読む形へ変更し、別packageで検証した。入力は全byte同一、rawが変わったのは修正対象index243だけで、他257入力・808,452,096バイトは同一である。失敗/raw/claimは保持し、expectedを失敗値へ合わせていない。失敗レポートのentriesは成功行だけなので、rawの固定strideで比較した。生成コード抜粋も保存した。

元イレグは次に既存のtarget-counter入力制約に当たった。準備済み定義はtargetがenemies_random:1で、ポリシーは既にworld_scope=single_body、body0/generation1と明示されている。body bindingが1個だけである場合、対応済み敵selectorは必ずbodyへ戻るため、counterの入力route/policyだけをbodyへ正規化する。元定義・準備済みtarget文字列は保持し、CPUで抽選しない。部位/add等のbindingがある世界とphysical_actor宣言は受付を広げていない。GPUの既存actor数1制約も維持した。

実編成package `40ecd50ac0d4b99b2a192ed8268115c11d8698c68b5cf63a40e6d7f9156a8766` は、全76定義の3/30秒をMetalと独立sealで一致させた。3秒では未発火、30秒では6hit branchのcast/landing handler2回と通知6回がある。原13hit条件のbranchは未発火で、13hitのGPU証拠は合成だけである。元の全射撃・状態・ダメージも既存実編成比較器で照合し、追加2入力のために258を再実行しなかった。

CPUは23群169検査(skip0)47.733秒、native事前13.616秒、Metal4.340秒。実編成はCPU2群10検査12.324秒、native2.027秒、Metal2.978秒。影響する既存counter/world-roster/分類の26検査も成功した。CUDA/MSLは同じSlangから生成し、両実行は生成cache必須hit・実行時Slang0である。実編成のMetal library/pipelineは既存キャッシュを使い、それぞれ約0.002秒だった。現CUDAの計算・driverキャッシュは今回検証しておらず、Windows追加操作0である。

実行前は258＋実編成2の非圧縮input/readbackと14GiBの予約を見積もった。完了済みrawのゼロ領域を全内容/SHA/path/inode保持で疎化し、計2,488,532,992バイトの割当を回収した。削除はない。静的受付240/266、base180/203、残35分類で、旧239プロフィールの記録・入力SHAは全て保持した。

次は新しい保留キューのライブ再入とcapacityを直す。現在は生成開始時のcountをsnapshotするため、生成中に再び新modeを保留する場合のtailは次回へ残り、正本の新queueのlive iterationとは未一致である。0ヒットでも正本の照会は必要だが、現在の共通sample経路は使わない金額の計算も行うため、極端な係数でのoverflow等を避けるquery-only経路が必要である。HP basisは既存のpending受付guardで閉じており、照会順の契約と接続が残る。receipt範囲の移動は現在8word本体をcopyしており、部位/interruptや周期snapshotのsidecarも持つtailでは追加の移動契約と実装が必要である。ランダム対象・部位/interrupt・他の実編成、現CUDAも未完了である。これらを13契約の成功で認定しない。全キャラ認定0、通常UI CPU、全目標未達を維持する。

CLI suiteは `full-burst-landing-retention` と `full-burst-landing-rosters`。展開した固定packageのcwdで生成のみの事前検査、生成cache必須のrun、保存結果sealを行う。記録は `research/portable-full-burst-landing-gpu-checkpoint.json`、`research/full-burst-landing-gpu-evidence/`、両suiteのexpected JSONにある。次の実装はこの残件と[正本契約](portable-full-burst-landing-reference.md)から続ける。
