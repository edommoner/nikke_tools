# 共通の弾数・チャージ時間の量補正

`gpu/quantity_runtime.slang` にソース別の丸めを実装し、CUDA／Metalの武器実行器へ接続しています。既存の効果コンパイラーからグループ・ソース・排他指定を梱包し、両GPUの計算・定義・fixtureを共用します。CPUで計算した有効弾数やチャージ期限は入力にしません。

## グループと数値設計

グループは、所有者・ソースタグ・明示グループ（なければ定義の識別子）・排他指定で分けます。同じグループの有効な成分を登録順に合算してから、一度だけ量へ変換します。別キャラ・別ソースを表示名だけで同一グループにまとめません。`_source_tag` と `_quant_group` は計算用の情報として保持します。

グループの百分率p、基礎値B、刻みsに対して、`floor((B × (p / 100)) / s + 0.5) × s` の順に共通binary64で計算します。弾数の刻みは1発、チャージ時間は0.01秒です。負の半端も正方向へ丸めるため、ダメージや定額弾数の偶数丸めとは区別します。

最大弾数は基礎弾数＋丸め済みの増減＋定額増減で、定額分は合計後に偶数丸めします。ここで整数をfloatへ戻して足すと、大きな増減を相殺したときに基礎弾数を失うため、加算は検査付きint64で行います。`基礎16 + 2^60 − 2^60 = 16` のケースを検証しています。中間int64の範囲外、または正の弾数が状態領域の上限を超える場合はstatus 2で拒否し、黙って切り詰めません。最終的な弾数の下限は1発です。

`max_ammo_reduction_exclusive` はグループ合算後の符号で判定します。有効な負の排他グループがあれば、すべての減少グループのうち最大の減少だけを残します。増加は残し、正の排他指定や、相殺されて0になった排他グループでは減少の選別を始めません。

## 状態への接続

- 開始効果の適用後に初期弾数を決めます。通常武器の最大弾数が増えても、その場では補充しません。減少した場合は余分な弾を削り、装填の完了ごとに最大弾数を再計算します。
- 有限の武器変更モードは `max_ammo_buff_applies` を解釈します。有効な場合も、モード進入と装填完了で計算した弾倉を保持します。無限モードの同指定やカウンター比例のモード弾数は未対応として拒否します。
- チャージ速度はグループごとに0.01秒へ丸めて引き、下限0を適用した後に `charge_time_flat` を足して、もう一度下限0へ制限します。判定前は毎フレーム再計算し、補正の失効で期限が変わる場合も扱います。0秒になれば開始フレームで発射でき、周期下限は従来どおりチャージ開始時刻を基準にします。
- 施術者基準の速度補正は、メタデータの元のチャージ時間から受領者の百分率へ換算してからスタックを乗算します。育成による表示時間の上書きとは区別します。元のチャージ時間を持たない施術者の成分は集計へ登録せず、空のグループで浮動小数点の加算順を変えません。
- 速度の増加／減少免疫は、合算したグループの符号へ適用します。装備・キューブは免疫から除外し、残った速度を使って時間と超過分のダメージ変換を計算します。
- 固定チャージ時間の存在は速度・定額時間の補正と速度超過分の変換を抑制します。明示値が複数なら施術者自身の最新の適用時刻、同時刻なら登録順で選びます。値を持たない固定マーカーは基本時間を保持します。

条件、期限、スタック、同期間の子通知は既存の共通実行器を使います。免疫、量補正、固定時間のためにMac専用の効果定義やキャラ分岐を追加しません。

## 同名装備に関する既知のCPU差異

既存CPUは、同じ表示名の装備成分を量のグループ集計より前に1個へまとめる場合があります。この挙動へ合わせて成分を捨てる処理は共通GPUへ移していません。明示された成分とグループで集計します。一般の同名スキル・対象別の複数キャリアは、引き続き別の接続作業です。

例えば基礎7発、同じグループの10%と20%の2成分なら、30%を一度丸めて2発を加え、最大9発・射撃後8発になります。既存CPUは最初の10%だけで最大8発・射撃後7発となります。`equipment-display-name-does-not-collapse-quantity-components` はGPUを手書き期待値の8発で検査し、CPUの実観測7発と既知差異も保存します。CPUとの全一致をこのケースの正しさの根拠にしません。

## 検証と効率化

### 2026-10-31 通常製品経路でのCPU規約

上記の独立成分モデルと通常製品計算を区別する。通常製品APIはCPU正本との一致を約束するため、`native_equipment_carriers` を明示し、同名・同stat・同対象・同max_stackの装備を既存の共有carrierで更新する。全定義、元の値、量グループを入力に保持し、定義を削除したり値を改変したりしない。変更するのは対象producerのmerge/search metadataだけで、共通Slangの状態・イベント処理、数量演算、丸めは同一。CPU正本と既存の独立成分テストは変更しない。

これはCPUの現規約との製品互換性であり、同名装備のゲーム仕様を新たに認定した意味ではない。独立成分を明示した従来の低水準経路は従来規約のまま保持する。通常製品について、異なるgroupの合算を意図したGPU側の規約を黙って適用しない。
