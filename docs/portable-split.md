# 共通均等分配と複合バフ対象（検証中）

固定ソース `d12b365`、ABI `0x50455666`。`received_dmg_split_even` と、複合バフ対象の順序付きリストを共通Slang実行器へ接続しました。CUDA／Metalは同じ効果定義、計算コード、入力ケース、CPU参照を使用します。通常画面はCPUを維持します。

## 分配と通知の契約

直接狙われたキャラの最終防御・被ダメージ補正でダメージを一度だけ計算し、下限1を適用した後、生存する分配メンバー数でsoftware binary64除算します。分配後に整数化したり各メンバーで防御を再計算したりしません。重なったグループは直接の対象を含むものだけの和集合で、間接的な連結はたどりません。順序は直接対象が先頭、続いて状態の登録順・状態内の対象順です。

各メンバーが自分の保護膜・遮蔽・デコイ・無敵・不屈を使います。被弾通知は直接の対象だけ、遮蔽被弾と致死通知は分配先にも送ります。メンバーと除数は最初の着弾前に確定します。途中の通知が状態を解除しても現在の一群は保持し、次の直接対象ではグループを再評価します。実行直前に倒れたメンバーは飛ばし、確定済みの除数は変えません。

参照は実際の `timeline.simulate` 内の `_boss_attack`／`_land_squad` と `BuffManager.split_group` です。既存CPUモデルとの互換性を検証するもので、ゲーム実測で未確定の分配順や通知仕様を新たに確定した主張ではありません。対象・遮蔽マスクは手書きの機械条件であり、自動照準・ボス予定などの世界処理は未接続です。

## 複合バフ対象

ネストした対象リストを静的な選択子の列へコンパイルし、順位・生存状態・対象順はGPU上で求めます。最大21回の受領順を保持します。重複は除去しません。受領者限定の状態通知では同じキャラへ複数回届け、通常の同名バフの一致判定にも順序と重複を含めます。一方、分配人数とメンバー集合では重複を除きます。10／11回の32bit境界と21回の上限を検証しています。

現在接続したのはバフの複合対象です。直接回復・弾薬操作などの複合instant対象は拒否を維持し、残る接続範囲として扱います。乱数など未対応の選択子をリストに包んでも受け付けません。バースト状態を使う要素にはGPUの戦闘状態が必要です。従来コンパイラーの定義＋補助選択子の合計256件という容量制約も維持します。

## 数値・配置と修正

入力86016／出力159744 words。旧版から入力16KiB、出力96KiB増加します。追加の被弾記録はコマンドごとに最大5×5件を保持し、最初の各直接対象の記録は旧位置に残します。広い対象順は出力領域に置き、Runtimeの宣言・配列は変更しません。Frameのフィールド数も同じですが、`value` を32bitから64bitへ広げました。一般的な8byte整列モデルではFrameは72→80bytes、32段で256bytes増える見積もりです。実際のレジスタ・spill・ピークメモリを測定した値ではありません。

致死通知の子効果で不屈が有効になるケースでは、HPと被ダメージ集計は正しい999でも、被弾記録だけがクランプ前の2000を保持する問題を検出しました。確定した量をフレームへ保存して記録も999へ修正しました。複合対象のCPU観測マスクにも重複を足し算する誤りがあり、集合のマスクへ修正しています。CPUの対象リストは変更せず、GPUから元の順序と重複を別に読み戻して比較します。診断は `research/portable-split-trace-failure.json` と `research/portable-split-oracle-mask-correction.json` に残しました。
