# 所有者付き周期資源とfeather

ABIは `0x50455654` です。共通Slangへ `periodic_source_refresh` と既存の `feather_refresh` を接続しました。個体ごとの寿命、現在の生存数、人口による周期短縮、名前付き `source_tick` とlegacyの `feather_tick`、参照命中数・buff倍率・最大HPで同じ資源を使います。CUDA／Metalで別々の計算実装やテストを作りません。

## 順序と数値

- 所有者の最初の登録順で処理し、その所有者の資源を登録順に走査します。
- 周期段階に入る際のkeyと所有者の集合を固定します。子通知で作った新しいkeyは次の段階へ回し、後で処理する既存keyが再登録された場合は、新しい記録を読みます。
- 現在の記録が子通知で置き換えられた場合、古い予約時刻からの更新で上書きしません。通知は観測時刻で発行し、同じ資源は1回のtickで最大1通知です。
- 生存判定は `expiry > t` です。0寿命は登録時点で0個体、-1寿命は無期限です。全滅後も登録済み0として残し、再召喚すると同じkeyの世代が進みます。
- 初回の予約は全slot数から計算します。以後は通知前に数えた生存数を使い、直前の予約時刻に次の間隔を足します。全滅を観測した予約は停止します。
- 間隔はCPUと同じ演算順で `base * (1 - reduction / 100 * (count - 1))`。時刻・寿命・間隔は共有software binary64を使い、Metalのfloat32へ置き換えません。

明示的なdescriptorは既存の `app/periodic_source_specs.py` と共有します。最大64個の所有者/name、1資源32slot、256入力定義を扱います。同じkeyを別の寿命・周期で再登録できます。名前にcolonが含まれる名前付きtickも保持します。参照値は登録済み資源ゲージ、周期資源、名前付きcarrierの順です。legacy featherの寿命・周期には元データの推定が含まれ、その既存の注意文をHTTP結果でも保持します。
