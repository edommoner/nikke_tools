# 周期対象・時計所有と同名DoT

元CPUのBuffManager・TimerRegistry・BossScriptとB3 controllerを独立に実行し、対象列の保持と時計の規約を確認してから共通Slangへ接続します。対象ごとの時計を独立に追加する設計ではありません。通常の周期効果は定義の時計を持ち、同じ発動者・同じ名前・単一スタックのDoTは一つの稼働中の時計を共有します。元CPUの世界処理は死んだ敵を `drop_enemies` で持続効果から除きます。共通側は捕捉したgenerationも検査し、再出現した個体へ旧対象を流用しません。

敵の選択列を持つ周期効果は初回登録の対象順を保持し、同じ定義の更新は対象を選び直さず期限を更新します。別の同名DoT定義が既存の時計を更新する場合は、新しい対象を末尾へ合併します。新しい名前付き保持グループのtarget登録は、本文脈の通知でも発動者の論理照準から対象を選びます。最初に稼働した定義の係数・間隔を保ち、今回の付与元のdurationで期限を更新します。最初の稼働者は宣言順の先頭とは限りません。既存の単一対象タイマーのgeneration規約は維持します。

時計は子通知より前に次の期限を消費し、同じDoTの更新は位相を保ちます。取消して再登録した時計は、その途中の走査へ参加しません。取消後に同名の別定義を強制発動する場合も、古い所有者索引を再利用しません。共通の索引版と全走査版の比較では、同じ計算・対象処理を使います。

`max_stack`だけでは周期ダメージ係数を増やしません。元CPUに合わせ、明示的な `scaling: stack_count` があるDoTだけが自身の現在stackを係数へ掛けます。外部リソースを参照する `scaling_ref` とランプ予約は引き続き未接続で、入力時に拒否します。

対象が空になっても、係数が非ゼロの通常の保持周期効果は論理ヒット・名前付き命中通知・該当するゲージ更新を維持します。着弾ダメージは0です。保持した明示対象へのsplit tickは、元CPUの `HitEvent.to` と同様、残った対象へ再分配しません。通常の非保持split選択の分配とは別の規約です。B3予約は元controllerがコピーした効果から遅延時に対象を解決する既存規約を保ち、保持対象の通常tickへ置き換えません。

ABIは `0x50455650`。周期定義の追加は512入力ワード、読み戻しの追加は3,072ワードで、既存余白に収まり入出力幅は各53,248ワードのままです。定義のflagsは保持対象・自身stack倍率・名前存在の3bit、groupは名前付き共有候補です。名前IDの0も有効なので、名前存在をID値から推測しません。GPUが実際の最初の所有者、捕捉対象順、世代、時計を決めます。CPUの選択結果や発動時刻列をGPU入力にしません。追加Runtime配列と定義フィールドの実GPU配置・メモリ増分は未測定です。

追加29ケースは対象順位8種、即時／遅延境界、複数ヒット、退場・再出現、同定義更新、同名合併、期限と係数の所有、最初の名前IDゼロ、取消・別定義での再始動、owner別分離、空対象の子通知、stack倍率、周期B3予約を含みます。28件は独立ダメージ・時計・BossScript参照、1件は独立B3 controller参照です。手書き期待値を読み戻しへ合わせて数値を緩めず、設計時の修正理由を `research/portable-periodic-design-corrections.json` に保存しています。

旧単体テストの未接続周期の拒否は、新しく必須となった保持ポリシーの検査へ変更しました。旧wire拒否ケースは保持ポリシーを欠いた周期入力として残し、不正group・名前存在・clock family・stack倍率等の拒否を追加しています。
