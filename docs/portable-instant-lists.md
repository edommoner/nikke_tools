# 共通instant対象配送（検証中）

固定ソース `60a10b6`、ABI `0x50455667`。順序付き複合対象を持つinstant効果を、CUDA／Metal共通Slangの再開可能な配送器へ接続しました。通常画面はCPUを維持し、全キャラ・全効果の対応を継続します。

## 配送と数値の契約

HP回復、現在HP減少、遮蔽回復・復活、保護膜・デコイ回復、弾薬操作、バーストクールタイム短縮は、最大21回の対象順と重複を保持します。対象は効果の開始時に全て選び、その後1対象ずつ実行します。子通知が完了してから次の対象へ進むため、回復通知が作成者の最大HPを変えた場合などは、次回の回復量の基準をその時点で読み直します。途中で順位を選び直すことはありません。

HP回復はゼロ・上限への回復でも受領通知を送ります。遮蔽回復は破壊済みの遮蔽を回復せず、ゼロ量でも通知を送りません。遮蔽復活も回復通知を送りません。保護膜・デコイ回復は既存の上限を基準とし、存在しない状態を作りません。弾薬の整数化・丸め・上下限・装填取消は既存の共通計算を再利用します。割合弾薬操作の完了通知は配送後に作成者へ1回だけ送り、対象が0人でも送ります。

部隊共有のバーストゲージは、対象に生存メンバーが含まれれば1回だけ加算します。対象の重複回数では増やしません。クールタイムは対象ごとに短縮し、その時刻を下限とします。これは実際のCPUハンドラーの区別です。

周期instantも同じ配送経路を使います。新規ケースでは既定の初回遅延と終了時刻の除外を検査しています。時刻・HP・量の計算はsoftware binary64の共通処理で、CPU計算結果をGPU入力へ渡しません。遮蔽回復の巨大な有限入力は、途中が無限大でも最後に有限の容量へクランプされる既存CPUモデルを保持します。新規の誤った拒否期待値を正例へ修正した記録は `research/portable-instant-lists-boundary-expectation-failure.json` に残しました。

## 修正した境界

初期のraw-wire診断では21対象の回復をGPUが5回だけ実行し、期待HP310に対しHP150でした。通常のホスト入力は当時この対象形式を拒否していました。現在は通常の入力コンパイラーで受け付け、全21回を実行してHP310になることをMetalで確認しました。初期診断は `research/portable-instant-list-admission-probe-metal.json`、修正後の通常入力の証拠は `research/portable-instant-list-normal-fixed-metal.json` です。

単純な対象の旧経路は保持し、複合対象だけを新しい配送器へ接続しました。入力86016／出力159744 words、Runtimeの宣言・配列とFrameのフィールドは前段から増やしていません。Frame.valueは前段と同じ64bitです。21回のHP回復は21枚の子フレームを積まず、1配送ずつ再開します。
