# 敵向け効果の受領者と出現世代（CPU参照段階）

GPUへ対象別の状態を接続する前に、参照する共通仕様とCPU側の保存・再付与・集計を整えます。これはv75のCPU参照段階です。GPUの状態保存、予約命中への対象保持、自律ルーティングはまだ接続していません。GPU ABIと生成物はv74のままです。

`enemy_recipient_specs` は、変更できない受領者の種類・ID・出現世代と、既存の対象名との対応を定義します。本体の物理部位は論理的な本体へ正規化します。未定義の飛翔体・シールドを暗黙に本体へ扱いません。対象の名前を書き換えたり、敵全体と全効果を掛け合わせた配列を作ったりせず、実際に発動したキャリアーへ受領者キーを保持します。

CPUの通常のbuffについて、次を既存の共通実行器へ接続しています。

- 通知が捕捉した対象を、現在の照準より優先して単一の対象を決める。
- 新規作成・再付与で、子通知より先に実際のキャリアーへキーを結び付ける。
- 同じ効果の再付与と、同名・同種の別定義をまとめる際に、対象名と出現世代の両方を一致させる。
- 集計計画と対象状態の条件を、評価する受領者のキーで絞る。死亡した対象と、同じIDで再出現した対象を区別する。
- スタック初期化は既存の受領者を保つ。対象カウンターのキャリアーは別の操作なので、通常の敵向けbuffとして付け替えない。

元のCPUコードで対象一覧ごとにまとめていた複数受領者の寿命・再付与規則は、この段階では変更していません。対象集合が重なる再付与を受領者ごとの独立更新へ移すこと、継続攻撃・予約命中の世代保持、削除／解除／状態参照の全経路は残っています。ここで全対象別効果の完成とは扱いません。

実際の `BossScript` の出現とHPプールを使い、本体・2体の追加の敵・再出現を18時点で確認します。通常の再付与、同名の別定義、発動者の違い、上限、失効、死亡、再出現前後の対象状態の条件を同じ表で扱います。古い対象名がキャリアーに残った状態でも、新しい世代へ効果を混ぜないことを必須にしています。これは明示的な参照モデルの検証であり、ゲーム内の全対象ルールを実機検証した記録ではありません。

この過程で、実際の通知名 `hit_count` に対しても親の対象を継承するよう修正しました。従来の `hit_count:` で始まる通知だけを扱っていた抜けを補っています。GPUのイベント8は既に同じ継承規約なので、GPUコードの置き換えは不要です。

機能確認版は `research/ports/v75-enemy-recipients-cpu-stage` に保存しています。その後、問い合わせのたびのキャッシュ全消去を、対象名ごとの出現世代・生存状態の監視へ変更しました。変化があれば既存の集計計画を破棄し、同じ世代・同じ状態なら、既存の対象名付きキャッシュを再利用します。入れ子の問い合わせや例外でも問い合わせ文脈を復元します。
