# CUDA／Metal共通コアの数値規約

## 2026-10-19 続きの到達点

整数変換・floor・コア命中確率用powを追加し、共通状態／イベント実行器をアプリのローカルHTTP APIからMetalへ接続しました。数値34,874ケースはbit一致、状態・イベント16ケースは既存の手書き期待値等と一致しています。再入上限とint64あふれの2件は実GPUで拒否しました。[接続済みの範囲と検証手順](portable-event-runtime.md)を参照してください。RTX 3070 Tiでも短い共通入力を実行し、数値5,178ケース・状態14ケースの出力ハッシュがMetalと一致しました。自律戦闘・通常画面のMetal計算・全キャラ対応は未完了です。

### 整数変換

`f64ToI64` は最近接・偶数丸め／0方向切捨て／floorを明示して選びます。NaN・無限大・範囲外はstatus=1とし、値0はエラー時の未使用値です。有効範囲は丸めた結果が `[-2^63, 2^63)`。CUDAの不正変換時のsentinelをゲームのダメージとして使いません。`f64FromI64` はint64からbinary64への偶数丸めを行います。

`f64Integral` はbinary64の整数値を返し、floorの大きな有限値をint64へ無理に制限しません。例えば2^64のfloorは2^64のままですが、その後int64へ変換すると失敗します。符号付きゼロを保存します。命中の偶数丸めと装弾の `floor(x+.5)` は別の演算順のままです。

### powの範囲と丸め保証

本体の2箇所の非整数べきは同じ `min(1, ratio^2.55)` です。今回の `coreProbability` はこの用途だけを扱います。入力は有限・非負、0は0、1以上は1。負数・NaN・無限大はstatus=2です。一般の `pow(x,y)` を実装済みとは扱いません。

0<x<1を x=m*2^-n、1<=m<2へ正確に分解し、t=(m-1)/(m+1)について `ln(m)=2*sum(t^(2k+1)/(2k+1))` の最初の64項を評価します。t<=1/3なので打切り誤差は `2/(129*3^129)*(9/8) < 2^-128`。ln(2)はQ128の連続する2整数で挟み、係数yは正確な入力binary64(2.55)です。有理数51/20へ置換しません。

z=y*(n*ln(2)-ln(m))の上下限を求め、2の指数を取り出して残差0<=r<1へ減らします。exp(-r)は47次までの交代級数を使い、次の項 `1/48! < 2^-128` を上限へ加えます。全段階でQ128の下向き／上向き丸めを行い、負の項では上限・下限を反転して減算します。固定小数点は192bitの整数領域を使い、この入力領域での整数部は64bit幅に収まります。

最後に両端をbinary64へ偶数丸めし、同じbit列になった場合だけ返します。不一致ならstatus=4で拒否します。近似値の誤差許容を広げて通す経路はありません。ln(2)の上下限、正確な係数、両級数の残差境界は `tests/test_portable_numeric_design.py` の独立した有理数検査でも確認します。全入力でstatus=4が発生しないという主張はしません。

期待値にはgmpy2 2.2.1のMPFR 4.2.1を使用し、256bitで下向き・上向きのpowを計算して、両端のbinary64丸めが一致することを確認します。CPUのlibm powとの近似一致を合格基準にはしません。正規／非正規の境界、ゼロへのunderflow、1付近、最終ダメージの丸め境界も検査します。MPFRは検証専用で、実行器は依存しません。[MPFRの丸め規約](https://www.mpfr.org/mpfr-current/mpfr.html)を参照してください。

以下の14,034ケースの記述は初回段階の履歴です。最新の実行記録は `research/portable-numeric-metal.json` にあります。

## 2026-10-19のMac実測と採用範囲

MacBook Air / Apple M5（GPU 10コア）/ 24GB / macOS 26.6.2 arm64、Python 3.12.15、Node 24.22.0、Slang 2026.20、Swift 6.3.3で確認しました。CPUカタログは203体、従来のMetal実証は4/4ケース成功です。WindowsやNVIDIA GPUは使用していません。

`gpu/binary64.slang` は、binary64のbit列を `uint64_t` に格納し、整数演算だけで四則演算と比較を実行する候補です。加減乗除は各演算で最近接・偶数丸めを行い、非正規数、符号付きゼロ、無限大を扱います。NaNは共通のquiet NaNへ正規化し、payloadは保存しません。大小比較・等値比較ではNaNはfalse、±0は等値です。

`gpu/numeric_probe.slang` はこの共通実装を呼ぶだけで、CUDA／Metalごとの数式はありません。`scripts/verify-portable-numeric.py` が入力・期待値・梱包・比較を共有します。Swiftは起動・転送・読み戻しだけです。Metalのコンパイルは `mathMode = .safe` とし、数値本体は浮動小数点演算を使いません。

手書き12ケース、境界値の組合せ1,734ケース、固定シードのbit列6,144ケース、近い指数の値6,144ケース、計14,034ケースをApple M5のGPUで実行し、全bitが一致しました。有限の四則演算の期待値は入力binary64を正確な有理数へ変換して計算し、最後に一度binary64へ丸めます。比較は入力binary64の順序を使います。CPUの戦闘トレースや発射時刻を入力へ流用していません。手書きの期待bit列は `tests/fixtures/portable-numeric.json` に一度だけ保持します。

この検証は全入力に対する証明ではありません。記録は `research/portable-numeric-metal.json`。CUDAはソース生成までで、NVRTCコンパイル・NVIDIA実行は未確認です。通常の詳細計算には未接続で、性能採用も未決定です。記録されたGPU時間は小さな独立演算群の一回のコマンド時間であり、本体の速度予測に使いません。

## 現行本体から分ける数量

| 数量 | 現行コードの例 | 共通コアへの方針 |
| --- | --- | --- |
| ID・種類・世代・順序・数・乱数 | `TargetRef`, `Order`, `timer_epoch`, `MTState` | 幅を明示した整数。桁あふれは受付／実行エラー。IDを実数に格納する旧wireは境界で検証して型へ変換する。 |
| 時刻・期限・間隔 | `when`, `timer_at`, `source_next`, `ready`, `fb_end` | 移植の最初はbinary64演算と既存の演算順を維持。単純なフレーム番号・マイクロ秒への切り捨ては採用しない。 |
| ゲージ・確率・HP比率・閾値 | `burst_amount`, `gauges`, `chance_acc`, `hp_edge_prev` | 二進小数の累積と閾値を維持。100の直前／直後、条件発動の順序を個別に確認する。 |
| 攻撃・防御・倍率・回復・容量 | `damage()`, `max_hp()`, `shield_current` | まず共通binary64で各演算の丸めを維持。表示用の丸めを中間状態へ持ち込まない。 |
| 1命中の整数ダメージ | `__double2ll_rn(d)` → `mx(...,1)` | signed int64への最近接・偶数丸めと範囲検査を共通化する。`floor(x+.5)`への置換は不可。共通コアに範囲検査付きの変換を実装済み。 |
| ダメージの合計・補償和 | `total`, `FloatSum`, `add_sum`, `finish_sum` | 演算順とNeumaier補償項も維持する。1命中が整数でもHP・分配等の途中値は整数とは限らず、全配列の一律uint64化はしない。 |
| 桁丸め・離散化 | 充填・装弾の `floor(...+.5)` | 使用箇所ごとの規約を残す。上記の命中丸めと統一しない。floor／切捨て／整数変換を共通実装済み。 |
| 非整数べき | コア命中期待値の `pow(ratio, 2.55)` | このclamp用途をQ128区間演算で実装し、最終命中丸めを跨ぐケースも検証済み。一般のpowは未実装。 |

現行の時計は `1/60` 秒、攻撃速度／充填速度の除算、反復加算、`1e-9`／`1e-6` の境界補正を混用します。例えば周期ダメージは初回の方針により終了境界を含むかが変わり、終了時には補正参照を `end-1e-4` へ寄せます。これらの比較を固定tickへ移すには、許容値を変えるのでなく仕様の境界を定義し直して独立の期待値を作る必要があります。

現行CUDAのビルドは `--fmad=false` です。共通コアでも積和を勝手に融合せず、式の結合順と各演算の丸めを保ちます。既存CPUとの一致は回帰検査であり、ゲーム仕様の根拠とは分けます。旧CPUの誤りが見つかれば仕様の期待値を先に直します。

## 次の本体接続

1. 整数変換、floor、有限判定、絶対値、clampされたpowは共通実装と検証を完了。演算単体の完了を全戦闘の互換性としない。
2. 現在の外部イベント用wireと状態を土台に、残りの効果・条件と武器／バースト状態を移す。分類・ID源は既存の共通定義を維持し、現行のdouble配列ABIを推測で使い回さない。
3. 共通時計の既存8ケースはMetalで通過。敵世界・対象世代・受領者別の時計を同じ実行器へ拡張し、通常戦闘へ接続する。
4. 現在の明示スタックと上限エラーを、残りの通知・ライフサイクルにも適用する。キャラ別のMetal分岐は作らず、生成物は手編集しない。
5. Windows用の薄いアダプターをRTX 3070 Tiで実行し、数値5,178ケースと状態・イベント14ケース、拒否2ケースを確認済み。同じGPUソース・入力・出力のハッシュがMetalと一致した。Windowsは必要な短い検証に限定し、常時テストやフルビルドは設定しない。
6. 実部隊・装備・一時変更・発動順・最終HP・ダメージを確認し、小バッチから24GBでのピークメモリと処理時間を測る。通常画面のMetal選択はこの接続後に追加する。

全203体・全効果の受付を開くには、未対応の召喚／予約着弾／受領者別時計／同時命中も含めた実行器の完成と検証が必要です。標準条件187体のCUDAコンパイル受付や、今回の数値実証を完成件数に加算しません。

## 再実行

```sh
.venv/bin/python -m pip install -r requirements-validation.txt
.venv/bin/python scripts/verify-portable-numeric.py --validate-only
.venv/bin/python scripts/verify-portable-numeric.py
```

後者がMetal実行です。元の4ケースは従来どおり `scripts/verify-portable-probe.py --backend metal` で独立に確認します。両検証は同じSwift転送アダプターを使用します。
