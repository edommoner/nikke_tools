# 共通の資源・スタック参照命中数

`hit_count_gauge_ref`、`damage系:参照名`、通常の `scaling: stack_count + scaling_ref` を共通Slangへ接続します。CUDA／Metalで入力梱包・GPU実行器・期待値・比較スクリプトを共有し、途中のCPU数量・命中数・通知列をGPUへ渡しません。

## 優先順位と数値

1. `hit_count_gauge_ref` があれば資源だけを読み、未登録なら0。同名のバフへは進みません。
2. 数値suffixは静的命中数であり、`scaling_ref`より優先します。
3. 参照名suffixと通常ダメージのstack_count参照では、登録済みの資源を優先します。数量0も存在する値として扱います。資源が未登録なら、所有者と名前が一致する最初の有効なバフのstackを読み、どちらも未登録なら1です。

資源の整数部はソフトウェアbinary64の符号・指数・仮数から求め、int64への狭め変換を先に行いません。小数は0方向へ切り捨て、0以下の命中数は0回です。正の命中数は256までとし、それ以上はstatus 2で失敗させます。係数0の場合は元CPUと同様に参照命中数を評価しません。

命中数は発動時に一度確定して明示フレームへ保持します。命中通知の子が資源を減らしたり増やしたりしても、親の残りの命中数は変更しません。周期ダメージでは登録時ではなく各tickの発動時に確定します。通常の参照命中数は係数に二重乗算しません。

B3のplain bonus_damage予約は別の既存規約です。元CPUが命中数参照の分岐より先に予約へ進むため、予約数はそちらの既存規約を保持します。

## 配置

ABI `0x50455652`。参照packetは定義ごと4 words、資源の名前表256 wordsを入力の既存余白へ置き、入力57,344・出力65,536 wordsのstrideを維持します。命中数は既存フレームの用途が重ならないフィールドを使い、Runtimeの配列・定義フィールドは増やしません。

共通テストは935正例・135拒否、計1070入力となるため、ホストのバッチ上限を1024→2048へ拡張しました。実際に検証するのは固定1070入力であり、上限2048での性能・メモリを実測済みとはしません。GPUの実行上限120秒、Macのコンパイル上限300秒を維持します。

参照の資源キーをコンパイル時にdense IDへ結び、GPUは直接参照します。比較用の名前表全走査も同じSlang内のコンパイル切替に残し、両バックエンドで同じcontrol比較スクリプトを使えます。

## 検証と範囲

37件の専用ケースは、0と未登録、同名stack、所有者分離、最初のcarrier、各ダメージ系統、参照優先順位、小数・負数・256境界、命中途中の消費／補充、周期tickを含みます。元のBuffManagerとダメージ・敵ルーティングを独立参照します。さらに `research/portable-hit-reference-native-witness.py` は固定版タイムラインの実際の命中数決定ブロックをASTとして抜き出し、同じ37ケースを検査します。全バトルの認証を代用するものではありません。

初期の周期ケースには時計進行命令が不足していました。修正後はダメージ時計の期限ちょうどに最終tickが入ることもCPU／GPU双方で確認し、手書き期待値を5000→6000へ直しました。2回目のGPU入力SHAが同じであることを照合して保存済み出力を再比較し、この期待値だけの修正でGPUを再実行していません。資源instant時計の最終期限除外とは異なる規約です。

M5で37件、共通935正例・135拒否、全走査参照との全出力ワード一致、76単体テスト、固定負荷スモークが成功しました。実編成・HTTP・短いCUDA・順次測定の最終結果はチェックポイントに記録します。

資源倍率のfinite buffでの保持とinfinite buffでの追従、外部参照DoT係数、feather生存数、同一対象のramp、残る効果・世界・装備の接続は継続課題です。全変種認証は0/203体、通常画面はCPUを維持します。
