# フレームに固定した敵数の条件

v73では `enemy_count_above:N` と `enemy_count_below:N` を、単一本体を仮定した真偽値から、共通の世界状態を読む条件へ接続します。前者はN以上、後者はN以下です。条件の種類・整数の閾値とGPUの定義は `app/world_condition_specs.py` が管理し、ビルド時とロード時に生成定義との一致を確認します。キャラ名による分岐はありません。

敵数は本体1体と生存中の追加の敵の数です。物理部位や親参照から別の敵数を推測しません。v71で用意した `add_live_snapshot` を再利用し、フレームの世界遷移と敵攻撃の自爆を処理した後に一度確定します。射撃・スキルによる途中撃破では、そのフレームの値を変更しません。次の時刻の世界遷移で更新し、既存の状態集計キャッシュを無効にします。条件評価のたびに対象を走査せず、可変状態や命令幅を増やしていません。

永続効果は既存の実行時条件規約に従い、現在のサンプルを参照します。イベントで発動した時間付き効果は、発動時点の条件を満たせば持続時間の間残ります。時間付きの条件付きpassiveは、既存の期限延長規約を使い、条件が成立している間は延長し、条件が外れた後は最後の期限まで残ります。この寿命処理を敵数条件専用に複製していません。

検証は同じ共通の効果集合へ出現・撃破・再出現・時間切れを入力し、敵数・攻撃力・クリティカル率／ダメージ・チャージ倍率・条件付きイベントの実発動数を観測します。CPUの実際の世界実行器とバフ管理器へ同じ外部刺激を渡し、独立した期待値とも比較します。物理部位がある場合も同じ効果集合を使います。キャラごとの同内容のテストは追加しません。これは現在の明示的な世界モデルの照合であり、ゲーム実機で敵数の全規則を検証したという意味ではありません。

動的条件の機能確認版は `research/ports/v73-world-conditions-native-stage` に保存しています。その後の効率化では、検証済みの世界に追加の敵の出現元が存在しない場合だけ、敵数を1へ事前確定します。「現在生きている追加の敵が0体」は根拠にしません。遅れて出現する敵の条件を誤って固定しないためです。事前確定には既存の定数条件を再利用し、寿命・発動順・対象や装備の命令は変更しません。標準条件で受付済みの187体の生成命令全体と武器入力が前段階と同一であることを確認しています。

通常の召喚受付・対象別効果・実射撃からの同時命中通知は、この敵数条件だけでは完成しません。その後のv74で `target_is_boss/add` を[通知の対象を保持する共通文脈](target-context-runtime.md)へ接続していますが、自律照準と対象別の効果保存は残っています。通常計算の召喚受付は引き続き拒否し、残る16体や宝もの・装備・敵世界の全組み合わせの対応を完了扱いにしません。

native/PTXの両方で、共通の条件集合を16時点ずつ、部位なし／ありの2ケースで確認しました。既存の出現元13ケースも両方で通過し、軽い共通検査92件、既存の混成10部隊、所持装備を含む通常APIも通過しています。通常APIではマクスウェルを含む部隊のGPU単独・CPU照合付きGPU・CPUが一致し、一時的な攻撃力変更で合計843,441,244から852,186,159へ変わることも確認しました。以前の命中5ケースと世界／被弾7件は、CUDAの差分が新条件とABI以外にないことを全文比較した上で再利用し、今回の再実行件数へ加えていません。

事前確定の速度測定では、同じ8候補の通常APIは単回比較で5,426.4109msから5,763.676msとなり、高速化を確認できませんでした。実際の45秒部隊計算8候補を同一コンテキストで交互に3回ずつ測ったGPU時間の中央値は、動的条件5,428.689ms、事前確定5,354.131msでした。差は約1.4%で、測定ごとの揺れもあるため、安定した高速化や全体の高速化とは判断しません。事前確定は不要な動的評価を省き、既存187体の生成命令と従来の検証根拠を維持する処理として残します。確定記録は `research/world-conditions-checkpoint.json`、交互測定は `research/world-conditions-specialization-benchmark.json` です。
