# 部隊編成探索の設計メモ

状態：実装中（2026-11-06〜、ブランチ `codex/team-search`）。作成 2026-11-05。

ChatGPTの「部隊編成最適化アルゴリズムの設計提案」をClaudeが精査し、このリポジトリの現状と照らして修正した方針をまとめる。実装はAGENTS.mdのClaude–Codexワークフローで単位ごとに進める。

## 目的

所持・育成済みのキャラから5人と配置・バースト運用を選び、ユーザーが指定した戦闘条件で最良の編成を探す。既存の強編成を再現するだけでなく、Tier表や回帰用編成例に頼らず、スキル仕様と戦闘シミュレーションを根拠に未知の強編成を見つけられることを目標とする。

結果は「探索で見つかった最良候補」として報告し、数学的に保証された最適解とは区別する。

## ChatGPT提案から採用するもの・変えるもの

採用する原則：

- ハード制約とソフト評価を分ける。成立しないことが確定していない編成は残す。
- 単体性能の低さだけでキャラを除外しない。
- 高速な評価と詳細な評価を分け、取りこぼしを測定する。
- 「最適解」と「最良候補」を区別する。

変更する点：

1. **探索アルゴリズムは主要な問題ではない。** 5人の組み合わせ（全206体で約29.4億、所持150体で約5.9億）は、軽い近似評価なら全列挙できる。遺伝的アルゴリズムは使わない。ビーム探索は重複なし5部隊の組み合わせにだけ使う（既存の `bestDisjoint`）。
2. **詳細シミュレーションを早い段階から使う。** CPU並列化で詳細計算が安くなったため、近似評価は「明らかに弱い候補を落とす」程度の薄い層でよい。
3. **シナジー表を手作業で作らない。** 2人・3人の組み合わせ表は維持できない（3人の組だけで約144万通り）。近似評価は、エンジンが既に持つ効果の中間表現から自動で導く。
4. **所持・育成状況と5部隊の重複なしを前提にする。** 提案は全キャラから理想の5人を選ぶ前提で、この観点がなかった。
5. **バースト運用を探索の変数にする。** 配置だけでなく、周期の指定も編成ごとの候補として評価する。

## 構成

| 層 | 内容 |
|---|---|
| L0 入力 | 効果の中間表現、所持・育成データ、ユーザーが設定した戦闘条件 |
| L1 制約 | ハード制約、配置の同値類 |
| L2 近似評価 | キャラの性能表とグループ計算による評価。全列挙と枝刈りで上位K件と多様性の保管庫を作る |
| L3 詳細評価 | 上位候補をCPU並列で詳細計算。配置の同値類 × バースト運用の候補 |
| L4 局所改善 | グループ値から予測で絞った1人入れ替え、配置・運用の変更、重複なし5部隊の組み合わせ |
| L5 確認と報告 | 任意の複数条件チェック、取りこぼし率の測定、最良候補として報告 |

### L1 ハード制約

- 所持している、同一キャラの重複不可、モード固有の制限（企業限定など）、レイドの部隊間で重複しない、ユーザーが指定した必須・除外。
- フルバーストの成立、バーストゲージの回転、CT短縮による周期は制約にせず、評価で扱う。
- エンジン未対応のキャラは黙って除外せず、件数と理由を結果に出す。

### 配置の同値類

配置が結果に影響するのは、次の2つだけである。

1. 同じバースト段階の中での自動使用の優先順（部隊の並び順。上流 `calculator/timeline.py` の `_rebuild_burst_order`）。
2. 位置を参照する効果。

中間表現から位置を参照する効果を静的に検出し、それ以外のメンバーの入れ替えは同じ配置として扱う。統合が正しいかは、ランダムに選んだ配置を実際に計算し、結果がビット単位で一致することで確認する。

### バースト運用の候補

ゲーム上の規則（ユーザー確認済み）：

- 手動：同じ段階の先頭の候補がクールダウン中なら、戻るまで待つ。
- 自動：クールダウン中なら次の候補へ回る。

上流の既定は「B1/B2は待つ、B3は次へ回る」の混在で、手動・自動を切り替える選択肢は製品側にない。運用の選択肢として「手動（待つ）」「自動（次へ回る）」を分ける必要がある。基本は「待つ」とする。

既存の周期指定で表現できる例：

| やりたいこと | 指定 |
|---|---|
| マストを3の倍数回に使う | マスト `every:3`（運用 `mast3`） |
| マストの効果をB3のXに載せる | マスト `every:3`、X `[3,6,9,…]` |
| プリカは初回だけ、以降はミント | プリカ `[1]`、ミントは指定なし |

周期を指定したキャラは、自分の番ではない回は優先順位の最後尾に回るだけで、他に使える候補がなければ発動する。

探索では、編成ごとに次の規則で運用の候補を自動生成し、最良のものを採用する。

- 基本：待つ（手動）／次へ回る（自動）。
- 特定の周期で効果が大きいキャラがいれば、その周期を優先する案と、各B3と周期をそろえる案。
- 同じ段階に複数いれば、1人を初回だけ、以降は別の1人にする案。

1編成あたり2〜6通り程度を想定し、L3で配置の同値類と一緒に評価する。「周期で効果が大きいキャラ」の判定に名前分岐は使わず、効果データの条件（周期回数など）から導く。

### 敵条件

敵条件はユーザーが設定する。対象のボスがわかっている人が設定する方が、推定より正確で速い。

| 情報 | 入手先 | 状態 |
|---|---|---|
| ボスのHP・防御・攻撃・属性 | enikk.app GraphQL（認証不要） | 取得可能。プリセットに反映済み |
| 部位のHP比率・破壊設定 | 同上 `parts_obj` | 取得可能 |
| ボスのスキルの威力係数・狙う対象・弾数・弾速 | 同上 `monster_obj.skill_data` | 取得可能 |
| 行動の時系列（いつ何を撃つか） | 公開データなし（行動ツリー名のみ） | ユーザー設定 |
| コアの有無・大きさ・位置 | 公開データなし | ユーザー設定 |
| 距離、フェーズ・部位ごとの有効射程 | 公開データなし（攻略記事に定性的な記述のみ） | ユーザー設定 |

主な探索はユーザーが設定した1条件で行う。複数の条件（コアの有無、距離の近・中・遠など）での確認は、最終の上位候補だけに行う任意のオプションとする。計算時間は条件数に比例するが、上位だけに絞れば小さい。条件を少し変えると順位が大きく崩れる編成に注意を出す用途を想定する。

### 取りこぼしの抑制

近似評価で全列挙すれば、探索アルゴリズムによる見落としはなくなり、残るのは近似評価の誤差だけになる。

- 近似評価と無関係にランダムな編成を一定数詳細計算し、近似評価の上位K件に真の上位100件の何%が含まれるかを測る。99%以上になるKを採用する。
- 詳細計算の結果で近似評価の誤差を補正する。
- 上位編成について、1人ずつ所持キャラ全員と入れ替えて詳細計算する。
- 戦術の異なる編成を保持する多様性の保管庫を作る（バースト構成、属性、武器種などで区分）。
- 現在の候補生成の起点である回帰用編成例は、検証用の既知編成として使い、候補生成の起点からは外す。

## グループ別の限界価値による効率化

### ダメージ式の構造

上流 `calculator/damage.py` のダメージは7グループの積で、グループ内は加算である。

```
ダメージ = ①係数 × ②攻撃−防御 × ③ボーナス × ④チャージ × ⑤種類別ダメージ × ⑥被ダメージ × ⑦優越コード
```

グループ i の現在値を B_i とすると、x を加えたときの倍率は (1 + x / B_i)。バフの価値は現在値に反比例し、グループ i の a とグループ j の b は a / B_i = b / B_j で等価になる。例：⑤が2.5、有利属性の⑦が1.1のとき、⑦の+10%（+9.1%）は⑤の+10%（+4.0%）の約2.3倍の価値がある。

注意点：

- ②は「攻撃力 × (1 + 攻撃力%) + 固定加算 − 実効防御」。施術者基準の攻撃力バフは固定加算として入る。限界価値は「加算量 ÷ (実効攻撃力 − 防御)」で、防御が高いほど大きい。
- ③はクリティカル（発生率 × (0.5 + クリティカルダメージ)）、コア、有効射程、フルバースト+50%の加算。フルバースト中はクリティカル系の効きが薄まる。
- ⑤はダメージの種類ごとに対象が異なる（バースト、貫通、継続ダメージなど）。
- グループ値は時間帯で変わるため、指標は攻撃ごとの「ダメージ ÷ その時点のグループ値」の合計（ダメージで重み付けした値）とする。
- 装弾数、リロード、攻撃速度、チャージ速度、バースト周期は攻撃回数を変えるもので、グループ計算には現れない。

### キャラの性能表

キャラごとに一度だけ作る。

- 攻撃の内訳：ダメージの種類別・時間帯別（フルバースト中かどうか）の攻撃回数と基礎ダメージ。
- 配るバフ：グループ、量、対象（自分・全員・攻撃力上位など）、有効な時間帯。

バフは効果データから静的に読む。有効な時間帯と攻撃回数は編成に依存するため、2〜3種類の標準編成で短く実行して測る。所持150体で数百回、CPU並列で数秒の想定。バースト周期は上流で確定しているゲージ式から構成ごとに計算する。

### L2 近似評価：グループ計算による全列挙

```
編成のダメージ ≈ Σ アタッカー Σ 時間帯 基礎ダメージ × Π グループ（基礎値 + 届くバフ）/ 基礎値
```

1編成あたり数百演算（約100ns程度の想定）で、所持150体の5.9億通りを10コアで数秒程度。3人以上のシナジーとグループ内の飽和は式に自然に含まれる。グループごとにバフを楽観的に足した上限値で枝刈りする。この枝刈りは近似評価に対して確実であり、詳細シミュレーションに対する保証ではない。

### L4 局所改善：予測で絞る入れ替え

詳細計算を1回すると、アタッカーごと・時間帯ごとのグループ値が得られる。これを使って入れ替えの効果を予測する。

- 入れる候補のバフ x の効果は、攻撃ごとに (B + x) / B 倍。掛け算の部分については近似ではなく正確。
- 外すメンバーのバフの効果は (B − x) / B 倍。本人のダメージは詳細計算の結果を使う。

5人×約145人の入れ替えをすべて予測し、上位10通り程度だけ詳細計算して最良に移る。改善がなくなるまで繰り返す。

| 1ステップの1人入れ替え | 総当たり | 予測で絞る |
|---|---|---|
| 詳細計算の回数 | 約725回 | 約11回 |
| カーネル単体（12ms/回） | 約9秒 | 約0.1秒 |
| 製品全体（約75ms/候補） | 約54秒 | 約0.8秒 |
| ブラウザWASM（10ワーカーで約107ms/部隊、S16） | 約78秒 | 約1.2秒 |

### グループ計算で表せない効果の扱い

- 攻撃回数を変える効果、バースト周期、味方の行動を条件にする効果（ミントとプリカの連動など）が大きいキャラには印を付ける。近似評価が低くても、一定数は必ず詳細計算に回す。
- 近似評価と詳細計算の差を記録し、キャラごとの補正値として学習する。

### 必要な計測値

攻撃ごとのグループ値、またはキャラ×グループごとの「ダメージ ÷ グループ値」の累計が必要になる。製品カーネルが出しているかは未確認。試作は、①〜⑦を攻撃ごとに計算しているPython参照エンジンでログを取り、カーネルを変更せずに始める。

## S19: L2 の C++ / WASM 高速化（2026-11-07）

`l2_compile.py` は S18 JSON を単一の version 1 フラット表へ変換する。自身の基準バケット、武器定数、付与元ATK、対象opcodeとメタデータを事前解決し、同じ `l2_fast/l2.cpp` を native shared library / CLI と standalone WASM にビルドする。`l2_fast.py build [--wasm]` は既存clang++/emsdkを使う内容アドレス付きignored cache。Python binding は明示ビルドが必要で、fallbackはない。`evaluate_s18.py evaluate --fast --out ...` は opt-in のみ。

Python 3.12 の `sum` は補償和であり、明示的な `+=` と `math.prod` は左から計算する。この差、付与元・buff・amount順、対象集合の重複除去と自身除外、静的cycleとRed Hood規則を維持した。S9全11,956、S1全2,460行（S18外部2,406＋CPU真値54）、seed固定random 200,000、全対象opcodeの合成258部隊で、native binding / CLI / WASM とoracleのメンバー値・合計をraw binary64比較し差分0。S18の全指標・残差・splitは完全一致、予測JSONはbyte一致。

Macの10M有効段階・順序付きrandomでnative単一thread中央値980 ns/部隊、10 threadsの集約kernel throughputは175 ns/部隊。WASMは1 worker 1,140 ns、10 workers 208 ns。Python 512部隊は152,440 ns。native単一threadは約156倍だが100 ns想定には約9.8倍の隔たりがあり、S9小標本の中央値は1,014 nsだった。150体の固定3人＋残り147体から順序付き2人を全列挙した21,462部隊はnative単一thread616 nsだが、9,120部隊は段階不足でcycleを省略するため速さの一因になる。増分演算による再利用は未実装。

150体の C(150,5)=591,600,030 は代表順序1つだけならnative 10 threadsでkernel約104秒の投影。順序はburst優先・位置対象・浮動小数点の加算順に影響するため、同値性を未証明のまま全順序を調べると120倍、約3.46時間（WASM 10 workers約4.10時間）。これは全列挙の実測ではなく、top-K保持等も含まない。丸めを維持するprefix/suffix再計算、配置同値類、L2上界による枝刈りが引き続き必要。精度・CPU参照・製品には変更なし。全測定（修正前harnessの測定も保存）、再現手順、制約は `team-search-v1/s19-report.md` と `s19/` に記録する。
