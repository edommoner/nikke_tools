# 部隊編成探索の設計メモ

状態：設計案（未実装）。作成 2026-11-05。

ChatGPTの「部隊編成最適化アルゴリズムの設計提案」をClaudeが精査し、このリポジトリの現状と照らして修正した方針をまとめる。実装はAGENTS.mdのClaude–Codexワークフローで単位ごとに進める。

## 目的

所持・育成済みのキャラから5人と配置・バースト運用を選び、ユーザーが指定した戦闘条件で最良の編成を探す。既存の強編成を再現するだけでなく、Tier表や回帰用編成例に頼らず、スキル仕様と戦闘シミュレーションを根拠に未知の強編成を見つけられることを目標とする。

結果は「探索で見つかった最良候補」として報告し、数学的に保証された最適解とは区別する。

## ChatGPT提案から採用するもの・変えるもの

採用する原則：

- ハード制約とソフト評価を分ける。成立しないことが確定していない編成は残す。
- 単体性能の低さだけでキャラを除外しない。
- 高速な評価と詳細な評価を分け、取りこぼしを測定する。
- 「最適解」と「最良候補」を区別する。

変更する点：

1. **探索アルゴリズムは主要な問題ではない。** 5人の組み合わせ（全206体で約29.4億、所持150体で約5.9億）は、軽い近似評価なら全列挙できる。遺伝的アルゴリズムは使わない。ビーム探索は重複なし5部隊の組み合わせにだけ使う（既存の `bestDisjoint`）。
2. **詳細シミュレーションを早い段階から使う。** CPU並列化で詳細計算が安くなったため、近似評価は「明らかに弱い候補を落とす」程度の薄い層でよい。
3. **シナジー表を手作業で作らない。** 2人・3人の組み合わせ表は維持できない（3人の組だけで約144万通り）。近似評価は、エンジンが既に持つ効果の中間表現から自動で導く。
4. **所持・育成状況と5部隊の重複なしを前提にする。** 提案は全キャラから理想の5人を選ぶ前提で、この観点がなかった。
5. **バースト運用を探索の変数にする。** 配置だけでなく、周期の指定も編成ごとの候補として評価する。

## 構成

| 層 | 内容 |
|---|---|
| L0 入力 | 効果の中間表現、所持・育成データ、ユーザーが設定した戦闘条件 |
| L1 制約 | ハード制約、配置の同値類 |
| L2 近似評価 | 中間表現から導く軽い評価。全列挙で上位K件と多様性の保管庫を作る |
| L3 詳細評価 | 上位候補をCPU並列で詳細計算。配置の同値類 × バースト運用の候補 |
| L4 局所改善 | 上位編成の1人入れ替え、配置・運用の変更、重複なし5部隊の組み合わせ |
| L5 確認と報告 | 任意の複数条件チェック、取りこぼし率の測定、最良候補として報告 |

### L1 ハード制約

- 所持している、同一キャラの重複不可、モード固有の制限（企業限定など）、レイドの部隊間で重複しない、ユーザーが指定した必須・除外。
- フルバーストの成立、バーストゲージの回転、CT短縮による周期は制約にせず、評価で扱う。
- エンジン未対応のキャラは黙って除外せず、件数と理由を結果に出す。

### 配置の同値類

配置が結果に影響するのは、次の2つだけである。

1. 同じバースト段階の中での自動使用の優先順（部隊の並び順。上流 `calculator/timeline.py` の `_rebuild_burst_order`）。
2. 位置を参照する効果。

中間表現から位置を参照する効果を静的に検出し、それ以外のメンバーの入れ替えは同じ配置として扱う。統合が正しいかは、ランダムに選んだ配置を実際に計算し、結果がビット単位で一致することで確認する。

### バースト運用の候補

ゲーム上の規則（ユーザー確認済み）：

- 手動：同じ段階の先頭の候補がクールダウン中なら、戻るまで待つ。
- 自動：クールダウン中なら次の候補へ回る。

上流の既定は「B1/B2は待つ、B3は次へ回る」の混在で、手動・自動を切り替える選択肢は製品側にない。運用の選択肢として「手動（待つ）」「自動（次へ回る）」を分ける必要がある。基本は「待つ」とする。

既存の周期指定で表現できる例：

| やりたいこと | 指定 |
|---|---|
| マストを3の倍数回に使う | マスト `every:3`（運用 `mast3`） |
| マストの効果をB3のXに載せる | マスト `every:3`、X `[3,6,9,…]` |
| プリカは初回だけ、以降はミント | プリカ `[1]`、ミントは指定なし |

周期を指定したキャラは、自分の番ではない回は優先順位の最後尾に回るだけで、他に使える候補がなければ発動する。

探索では、編成ごとに次の規則で運用の候補を自動生成し、最良のものを採用する。

- 基本：待つ（手動）／次へ回る（自動）。
- 特定の周期で効果が大きいキャラがいれば、その周期を優先する案と、各B3と周期をそろえる案。
- 同じ段階に複数いれば、1人を初回だけ、以降は別の1人にする案。

1編成あたり2〜6通り程度を想定し、L3で配置の同値類と一緒に評価する。「周期で効果が大きいキャラ」の判定に名前分岐は使わず、効果データの条件（周期回数など）から導く。

### 敵条件

敵条件はユーザーが設定する。対象のボスがわかっている人が設定する方が、推定より正確で速い。

| 情報 | 入手先 | 状態 |
|---|---|---|
| ボスのHP・防御・攻撃・属性 | enikk.app GraphQL（認証不要） | 取得可能。プリセットに反映済み |
| 部位のHP比率・破壊設定 | 同上 `parts_obj` | 取得可能 |
| ボスのスキルの威力係数・狙う対象・弾数・弾速 | 同上 `monster_obj.skill_data` | 取得可能 |
| 行動の時系列（いつ何を撃つか） | 公開データなし（行動ツリー名のみ） | ユーザー設定 |
| コアの有無・大きさ・位置 | 公開データなし | ユーザー設定 |
| 距離、フェーズ・部位ごとの有効射程 | 公開データなし（攻略記事に定性的な記述のみ） | ユーザー設定 |

主な探索はユーザーが設定した1条件で行う。複数の条件（コアの有無、距離の近・中・遠など）での確認は、最終の上位候補だけに行う任意のオプションとする。計算時間は条件数に比例するが、上位だけに絞れば小さい。条件を少し変えると順位が大きく崩れる編成に注意を出す用途を想定する。

### 取りこぼしの抑制

近似評価で全列挙すれば、探索アルゴリズムによる見落としはなくなり、残るのは近似評価の誤差だけになる。

- 近似評価と無関係にランダムな編成を一定数詳細計算し、近似評価の上位K件に真の上位100件の何%が含まれるかを測る。99%以上になるKを採用する。
- 詳細計算の結果で近似評価の誤差を補正する。
- 上位編成について、1人ずつ所持キャラ全員と入れ替えて詳細計算する。
- 戦術の異なる編成を保持する多様性の保管庫を作る（バースト構成、属性、武器種などで区分）。
- 現在の候補生成の起点である回帰用編成例は、検証用の既知編成として使い、候補生成の起点からは外す。

## 決めること

1. 探索中のCPU照合を全件にするか、抽出にするか。全件では詳細評価が約2秒/回になり、L3の規模が大きく制限される。
2. 運用の選択肢として手動（待つ）・自動（次へ回る）を分けるときの既定値と表示。
3. 近似評価（L2）を作る前に、現在の簡易スコアと詳細計算の順位相関を測るかどうか。相関が十分高ければL2への投資は小さくてよい。

## 進め方

1. 現在の簡易スコアと詳細計算の順位相関、取りこぼし率を測る。
2. 手動・自動のバースト規則を運用の選択肢として分ける。
3. 配置の同値類（位置参照効果の検出とビット一致の確認）。
4. バースト運用の候補の自動生成。
5. 近似評価による全列挙と、多様性の保管庫。
6. 局所改善と、任意の複数条件チェック。

全キャラ対応が先行する前提とする。未対応のキャラが残ったまま探索を作り込むと、結果に偏りが出る。
